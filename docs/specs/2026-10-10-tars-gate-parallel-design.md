# TARS Gate Parallel — Design

Date: 2026-10-10
Status: 진행 중 — GP-M0(측정) · GP-M1(initrd 바꿔치기) 끝, 다음은 GP-M2.

사용자의 요청 한 줄에서 시작한다(2026-10-10).

> how to improve test gates time. research first.

## 한 줄 요약

루트 게이트는 22체인 × 2회 = 44판을 한 줄로 세워 1시간 00분 18초(BS-M1)가 걸린다. 빌드는 GL이 이미 첫 판으로 몰았으므로
남은 시간은 "체인 한 판 1~2.5분 × 44"이고, 그동안 호스트 코어 10개 중 대부분이 논다. 체인을 동시에 여럿 돌려 이 줄을 접는다.

## 배경 — 착수 전 조사 (2026-10-10, HEAD `8cb2ab4`)

1. 시간의 근원이 GL 때와 다르다. GL-M0~M3(`docs/decisions/project_gate_latency.md`)은 8할이던 빌드를 첫 판으로 몰았다.
   BS-M1 게이트의 `skipping make`가 43이다 — 44판 중 43판은 커널을 안 빌드한다. 지금은 부팅 · 타이핑 · 판정이 시간의 대부분이다.
2. 호스트는 10코어(성능 8 · 효율 2) · 32GB다. OrbStack VM은 `cpu: 10`, `memory_mib: 4096`이다. QEMU TCG(게스트 vCPU 1)
   하나는 코어 1~2개를 쓴다. 게이트가 순차이므로 대부분의 코어가 쉰다(GP-M0이 표본으로 확인한다).
3. 병렬의 바탕 하나는 이미 있다 — 체인마다 monitor · `hostfwd` 포트가 따로다(45455~45494, `docs/guides/lessons.md`).
   같은 체인의 1 · 2회차는 같은 포트를 쓰므로 체인 안의 회차는 순차로 둔다.
4. 병렬을 막는 공유 파일이 있다. 모든 체인이 `../kernel/initrd.cpio`를 `-initrd`로 읽는데 `make_initrd.sh`가 매 판 그 파일을
   제자리에서 `> initrd.cpio`로 자르고 다시 쓴다. 동시에 돌면 한 체인의 QEMU가 읽는 동안 다른 체인이 파일을 비운다.
   `zig build`(init · terminal)와 `kernel/build.sh`도 같은 트리에 쓴다.
5. 메모리. 게스트 512MB(`GUEST_MEM`)에 QEMU 오버헤드를 더하면 4GB VM에서 동시 3~4개가 상한이다. cold `zig build`(약 3GB)와
   겹치면 OOM이 난다(lessons "docker 작업은 한 번에 하나").
6. 고정 `sleep`의 정적 합은 한 판에 약 6분이다(copy 131초 · hangul 54초 · config 44초 · render 34초 순, polling loop 안의
   `sleep`이 섞인 값). 2회면 약 12분이다.

## 효과가 없는 것

- KVM · HVF — arm64 호스트에서 x86_64 게스트라 TCG 말고 길이 없다.
- `-smp` · TCG 멀티스레드 — 게스트 vCPU가 하나이고 부팅은 전체의 2%가 안 된다.
- 1~2분짜리 절약 — 게이트 잡음이 ±3분이다(lessons).

## 결정

1. 측정이 먼저다. 체인별 시간을 같은 게이트 안에서 잰 적이 없다. 병렬의 하한(가장 긴 체인)과 동시 실행 수의 근거(코어 사용률)를
   실측으로 얻은 뒤에 M2의 수를 정한다.
2. `RUNS`(2 → 1)는 이 서브프로젝트가 정하지 않는다. 사용자 결정 사항이다(`docs/decisions/feedback_gate_runs.md`).
   GP-M0 뒤에 사용자가 1로 정했다(2026-10-10, `a7ef734`). 같은 날 OrbStack 메모리를 4GB에서 12GB로 늘렸다(VM이 11.7GiB를 본다).
   그래서 M2의 추정은 1회 기준이다 — 체인 합 약 1,720초 + 빌드 236초, 가장 긴 체인 config 198초. 동시 4개 약 11분, 6~8개 약 8분.
3. 체인 스크립트가 빌드 스텝을 부르는 구조(`require_build_steps`)는 그대로 둔다. 병렬에서는 빌드를 게이트 시작에 한 번 순차로
   돌려 두고, 체인이 부르는 빌드는 전부 no-op이 되게 한다.
4. 판정은 바꾸지 않는다. 병렬이 드러내는 간헐 실패는 게이트 쪽 경합으로 보고 그 체인에서 고친다(lessons의 TC-M3 절과 같은 방식).

## Milestone

| | 무엇을 | 상태 |
|---|---|---|
| GP-M0 | `run_chain`이 회차별 초를 찍고 게이트 끝에 정렬된 표를 낸다. 루트 게이트 한 판 + 호스트 CPU 표본 | 끝(빌드 뒤 CPU 평균 57%, 체인 합 3,441초 + 빌드 236초) |
| GP-M1 | `make_initrd.sh`가 임시 파일에 쓰고 `mv`로 바꿔치기. 내용 해시 stamp는 뺐다 — 산출물이 매번 다른 바이트이고 아낄 것이 2분 남짓이다(M1 plan 확정 2) | 끝(tools 검사 1d, 1회 게이트 32분 23초) |

| GP-M3 | M0 표의 상위 체인에서 고정 `sleep`을 로그 관측으로(GL-M2 방식) | 필요하면 |
