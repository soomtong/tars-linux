# TARS Lessons Split — Design

Date: 2026-10-26
Status: design — 사용자 검토 전.

HANDOFF "다음 후보"의 첫 항목에서 시작한다(2026-10-24 프로젝트 점검이 남긴 둘 가운데 추천 1순위 (4). 사용자가 2026-10-26에 골랐다).

> `lessons.md` 1,700줄 — "이월 숙제" · "핵심 파일" 절은 각자 문서 하나 분량이다.

## 한 줄 요약

`docs/guides/lessons.md` 1,736줄을 다섯 파일로 나눈다. `lessons.md`는 규칙 · 게이트 운영 · 범용 명령과 "옮긴 절" 표를 가진 허브로
남고, 실측 · 안 되는 접근 · 이월 숙제 · 핵심 파일은 각자 파일 하나가 된다. 글은 한 줄도 고치지 않고 옮기며(제목 줄의 `#` 수와 허브의
머리말만 바뀐다), 실측 번호 1~92는 그대로다. 옛 참조는 고치지 않아도 허브의 표를 한 번 거쳐 닿는다 — 코드 · 스크립트 · 지난
plan/spec은 0줄 바뀌고, 그래서 게이트를 돌리지 않는다.

## 배경

### 지금의 모양

2026-10-26, HEAD `9dca7d3`. 절 경계는 `rg -n '^## '`로 쟀다.

| 절 | 줄 | 성격 |
|---|---|---|
| 머리말 · 규칙 셋 | 1~15 (15) | 이 문서가 무엇이고 무엇을 안 담는가 |
| 게이트를 돌리고 읽는 법 | 16~362 (347) | 명령 블록 + `###` 열넷 |
| 범용 명령 | 363~420 (58) | 명령 블록 하나 |
| 서브프로젝트를 넘어 유효한 실측 | 421~916 (496) | 번호 목록 1~92 |
| 시도했으나 안 되는 접근 | 917~1168 (252) | 글머리 목록 + `###` 하나 |
| 이월 숙제 | 1169~1292 (124) | 서브프로젝트별 체크박스(`[x]` 3 · `[ ]` 29) + 글 |
| 핵심 파일 | 1293~1702 (410) | `###` 다섯(`shared/` · terminal · init · 게이트 · 기억) |
| 꼬리 넷 | 1703~1736 (34) | IP-M2 · TR-M2가 남긴 것, 감독 루프의 구조, ghostty 프롬프트 인젝션 |

점검은 "이월 숙제 · 핵심 파일"을 짚었지만 줄 수로는 실측(496)이 가장 크고, 핵심 파일(410) · 게이트(347) · 안 되는 접근(252) 순이다.
이월 숙제는 124줄로 작다. 크기보다 성격이 다른 것이 문제다 — 게이트 절은 매 milestone 펴는 운영서, 실측과 안 되는 접근은 조사 전에
`rg`하는 사전, 이월 숙제는 할 일 목록, 핵심 파일은 지도다. 지금은 넷이 한 파일에 있어 `rg`가 다른 성격의 줄을 섞어 돌려주고, 할 일
목록이 사전 사이에 묻힌다.

### 참조는 두 가지 모양이다

`rg`로 셌다(이 문서와 `lessons.md` 자신 제외).

- 절 이름으로 — 지난 plan/spec이 `lessons "핵심 파일"`을 31번, `lessons "게이트를 돌리고 읽는 법"`을 9번, 그 밖의 `###` 제목을 열 번
  남짓 인용한다. 대부분 "닫을 때 lessons '핵심 파일'의 줄을 고친다" 같은 닫기 목록이다. 지금 읽히는 쪽(decisions · HANDOFF · README)에서는
  `"범용 명령"` 셋, `"안 되는 접근"` 하나, `"이월 숙제"` 여섯 남짓.
- 실측 번호로 — 스크립트 주석 여섯 자리(`dictation/check.sh`의 `lessons 45` · `dictation/probe.sh`의 `lessons 73` ·
  `dictation/stub.pl`의 `lessons 41` · `audio/probe.sh`의 `lessons 68` · `pointer/check.sh`의 `lessons 실측 53` ·
  `render/check.sh`의 `lessons 실측`), decisions 다섯 자리(`project_wireless` · `project_shell_memory` · `feedback_scripting_runtimes`).
  `terminal/src/vt_test.zig`는 실측 절의 문장을 따옴표로 인용한다.
- 파일 경로로 — `CLAUDE.md` "참고"의 한 줄, `README.md` 문서 표의 한 줄, 스크립트 주석 하나(`battery/check.sh`의 "포트 목록").

## 착수 전에 확인한 것

1. 실측 절은 `1.`부터 `92.`까지 빈 번호 없이 이어진다(`rg -n '^[0-9]+\. '`). 바깥 참조가 이 번호를 쓰므로 새 파일에서 번호가 1부터
   그대로 시작하면 참조가 산다.
2. 안 되는 접근 절 안의 `### 조사용 Zig 프로그램을 저장소 밖에서 돌리는 법`(1130줄)은 코드 블록에 `# ` 주석 줄을 가진다. 제목 수준을
   올릴 때 코드 블록 안의 `#` 줄을 건드리면 안 된다. 421줄부터 끝까지 코드 블록 안에서 `#`로 시작하는 줄은 그 1152줄 하나(`# `)뿐이고
   `### `는 없다(awk로 fence를 세며 쟀다). 그래서 `^### ` → `## ` 치환이 코드 블록을 건드리지 않는다. 코드 블록 밖의 `## ` · `### `
   줄은 열넷이다.
3. 꼬리 넷은 `##` 수준이라 어느 절에도 속하지 않는다. 성격으로는 IP-M2 · TR-M2(그대로 이월)는 이월 숙제, 감독 루프(init의 구조)와
   ghostty 인젝션(vendor 트리의 주의)은 핵심 파일이다.
4. `docs/guides/`의 다른 파일은 `completed.md` · `running-tars.md` — 영어 kebab-case 이름이다.
5. `git log -- docs/guides/lessons.md`가 51 commit이다. 파일을 나누면 옮긴 절의 `git log -L` · `blame`은 새 파일에서 끊긴다 —
   `git log --follow`는 이름 바꾸기 하나만 따라가고, 다섯으로 갈라진 것은 따라가지 않는다. `git blame -C -C`가 다른 파일에서 온 줄을
   찾는다.

## 결정

### 결정 1. `lessons.md`는 허브로 남고, 네 절이 새 파일로 간다

| 절 | 새 파일 | 줄(대략) |
|---|---|---|
| 머리말 · 규칙 · 게이트를 돌리고 읽는 법 · 범용 명령 | `docs/guides/lessons.md`(허브) | 440 |
| 서브프로젝트를 넘어 유효한 실측 | `docs/guides/measurements.md` | 500 |
| 시도했으나 안 되는 접근 | `docs/guides/dead-ends.md` | 255 |
| 이월 숙제 + 꼬리의 IP-M2 · TR-M2 | `docs/guides/carryover.md` | 140 |
| 핵심 파일 + 꼬리의 감독 루프 · ghostty 인젝션 | `docs/guides/key-files.md` | 435 |

게이트 절이 허브에 남는 이유 — 가장 자주 펴는 절이고, 지난 plan의 `lessons "게이트를 돌리고 읽는 법"` 9번과 지금 decisions의
`"범용 명령"` 셋이 고치지 않고 그대로 닿는다. 파일 이름은 `docs/guides/`의 관례(확인 4)를 따라 영어 kebab-case다.

### 결정 2. 글은 옮기기만 한다 — 바뀌는 줄은 셋뿐이다

바뀌는 줄은 다음 셋이고 그 밖의 줄은 바이트 그대로 옮긴다.

- (a) 제목 수준. 새 파일의 맨 위는 `# <절 이름>`이고(원래 `## <절 이름>` 줄에서 `#` 하나만 빠진다 — 글자를 더하지 않아야 결정 4가
  `#`만 걷어내고 견줄 수 있다), 그 아래 `### `는 `## `가 된다.
  꼬리에서 온 `## ` 절은 그대로 `## `다.
- (b) 새 파일마다 제목 밑의 머리말 두세 줄 — "lessons.md에서 2026-10-26에 떼어 냈다, 규칙은 허브의 것을 따른다".
- (c) 허브의 머리말 · 규칙 셋의 문장 중 "이 문서에는"을 "이 다섯 문서에는"으로 맞추는 몇 줄과 결정 3의 표.

글의 낡은 것을 고치거나 지우는 일(이월 숙제의 `[x]` 셋 등)은 이번에 하지 않는다(비목표 1). 섞으면 결정 4의 기계 확인이 "옮겼다"와
"고쳤다"를 못 가른다 — MS가 동작 변경과 옮기기를 Task로 나눈 것과 같은 이유다.

### 결정 3. 옛 참조는 허브의 "옮긴 절" 표로 닿는다 — 참조하는 쪽은 고치지 않는다

허브의 규칙 셋 바로 밑에 표 하나를 둔다. 옛 절 이름(지난 문서가 인용하는 글자 그대로)과 새 파일, 그리고 그 절의 `###` 제목들을 적는다.
"실측 N · lessons N은 `measurements.md`의 N번이다"를 한 줄 적는다.

고치지 않는 것 — 지난 plan/spec(기록이다), 스크립트 · 코드 주석(고치면 체인 스크립트가 바뀐 것이 되어 게이트를 불러야 한다 — 주석만이라도
"스크립트 0줄"이라는 확인이 더 값지다), decisions(`lessons 41`처럼 번호로 가리키는 것은 표 한 줄로 닿는다).

고치는 것 — 문서의 구조를 말하는 자리 셋. `CLAUDE.md` "참고"의 lessons 줄, `README.md` 문서 표의 lessons 줄, `HANDOFF.md`의 후보 (4).
셋 다 "lessons.md가 무엇을 담는가"를 말하므로 새 파일 넷을 함께 적는다.

### 결정 4. "옮기기만 했다"를 기계로 본다

MS의 `comm` 확인과 같은 모양이다.

- (a) 줄 집합. 옛 `lessons.md`(`git show 9dca7d3:docs/guides/lessons.md`)와 새 다섯 파일을 이어 붙인 것을, 각자 줄 머리의 `#+ `를
  걷어낸 뒤 정렬해 `comm -3`으로 견준다. 옛 쪽에만 있는 줄은 0이어야 하고(바뀐 머리말 몇 줄을 빼면 — 그 줄은 plan이 미리 적는다), 새
  쪽에만 있는 줄은 결정 2의 (b) · (c)뿐이어야 한다.
- (b) 순서. 옮긴 절 하나하나에 대해 옛 파일의 그 줄 범위와 새 파일의 본문을, 같은 `#` 걷어내기 뒤 `diff`해 빈 출력을 본다 — 줄 집합만
  보면 절 안에서 순서가 바뀐 것을 못 잡는다.
- (c) 표의 자리가 실제로 있는가. 결정 3의 표에 적은 `###` 제목 하나하나를 그 새 파일에서 `rg -F`로 찾는다.
- (d) 번호. `measurements.md`에서 `rg -c '^[0-9]+\. '`가 92이고 첫 줄이 `1.`이다.

### 결정 5. 게이트를 돌리지 않는다

바뀌는 파일이 `docs/guides/` · `CLAUDE.md` · `README.md` · `HANDOFF.md` · 이 design · plan · 기억뿐이다. 빌드에 들어가는 것도 체인이 읽는
것도 없다 — `git diff --stat`에 그 밖의 경로가 0인 것을 확인으로 삼는다.

### 결정 6. milestone은 하나, commit은 Task마다

- Task 1 — 네 파일을 만들고 허브를 줄인다(결정 1 · 2 · 3의 표). 결정 4의 (a)~(d). commit 하나.
- Task 2 — `CLAUDE.md` · `README.md`의 lessons 줄. commit 하나.
- Task 3 — 닫기(아래 "닫을 때"). commit 하나.

Task 1을 하나의 commit으로 두는 이유 — 옮기기는 원자적이어야 한다. 절반만 옮긴 상태는 같은 글이 두 곳에 있거나 어디에도 없다.

## Milestone

- LS-M0 — 위의 Task 셋. plan `docs/plans/2026-10-26-tars-lessons-split-ls-m0.md`.

## 위험

1. 옮기다 줄이 빠지거나 겹친다. 경계가 `## ` 줄이라 잘라내기 범위를 한 줄 틀리면 빈 줄 하나나 제목 하나가 사라진다. 결정 4 (a) · (b)가
   막는다.
2. `###` 올리기가 코드 블록 안을 건드린다. 확인 2에서 대상이 없음을 쟀고, 결정 4 (b)가 `#`를 걷어낸 뒤 견주므로 수준 말고 다른 것이
   바뀌면 드러난다.
3. `blame`이 끊긴다(확인 5). 받는다 — `git blame -C -C`가 있고, Task 1의 commit 메시지에 옛 파일과 commit을 적는다.
4. 다음 사람이 새 실측을 `lessons.md`에 쓴다. 허브의 규칙 셋에 "새 항목은 성격에 맞는 파일에"와 각 파일의 이름을 적는다. 그리고 지난
   plan의 닫기 목록이 "lessons '핵심 파일'의 줄을 고친다"라 적혀 있어 다음 plan도 그것을 베낀다 — 표가 그 한 번을 이어 준다.
5. 허브 표의 절 이름이 낡는다. 옮긴 뒤에는 새 파일 쪽 제목이 정본이고, 표의 "옛 이름" 칸은 지난 문서가 인용한 글자라 바뀌지 않는다.

## 비목표

1. 글의 정리 — 이월 숙제의 닫힌 `[x]` 셋, 낡은 실측, 꼬리 IP-M2 · TR-M2의 현재성. 옮긴 뒤 각 파일이 작아져야 보이는 일이고, 필요하면
   다음 후보로 적는다.
2. 참조하는 쪽(스크립트 · 코드 주석 · decisions · 지난 plan/spec)의 편집(결정 3).
3. 실측 번호의 재배열이나 주제별 묶기 — 바깥 참조가 번호를 쓴다(확인 1).
4. 소개 페이지(`gh-pages` `data.js`). 내부 작업이다(사용자 결정, 2026-10-25).
5. 점검의 나머지 (5) `.github`.

## 닫을 때(lead의 몫)
