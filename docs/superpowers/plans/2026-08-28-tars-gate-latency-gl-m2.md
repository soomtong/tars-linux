# TARS Gate Latency GL-M2 Implementation Plan

> **협업 방식(이 저장소 규칙):** 구현 파일 편집은 **사용자**가 한다. 각 Step의
> "넣을 것"/"지울 것"을 그대로 넣으면 된다. 빌드·검사·QEMU·게이트 실행과
> git commit은 **Claude**가 한다.

**Goal:** 게이트가 키를 보낸 뒤 **눈감고 0.3초를 기다리는 것을 그만둔다.**
로그가 자라는 것을 보고 다음 키로 넘어가되, 아래로 0.05초 위로 0.3초로 가둔다.

**Design doc:** `docs/superpowers/specs/2026-08-26-tars-gate-latency-design.md`의
"재개 (2026-08-28)" 절. 결정 5·6·7·8이 내용을 이미 정해 두었다.

**Architecture:** 저장소 루트에 `gate_lib.sh` 하나를 만들고, 지금 `type_keys`를
각자 갖고 있는 다섯 체인과 인라인 `for` 루프를 갖고 있는 한 체인이 그것을
`source` 한다. **Zig 코드는 한 줄도 안 바뀐다.**

**Tech Stack:** bash, QEMU monitor

## 착수 전에 이미 확정된 사실 — 다시 조사하지 않는다

### 세어서 확인한 것

회차당 0.3초짜리 키가 **492개**이고 **147.6초**다. 3회차를 곱해 **7분 23초**,
22분 게이트의 **33%**다.

| 체인 | 0.3초 키 | 회차당 |
|---|---|---|
| copy | 151 | 45.3초 |
| input | 139 | 41.7초 |
| render | 82 | 24.6초 |
| config | 57 | 17.1초 |
| power | 48 | 14.4초 |
| terminal | 15 | 4.5초 |

**세는 방법에 함정이 둘 있었다.** `render`의 `type_keys`는 줄 끝의 `\`로 이어져
있고 `config`·`power`는 인자가 배열이다. 줄 단위로 단어를 세면 각각 32·2·2가
나온다 — **실제로 처음 그렇게 세서 합이 341로 어긋났다.**

### 소스를 읽어 확인한 것 다섯

**1. 여섯 체인의 `set` 옵션이 전부 `set -uo pipefail`이다.** `-e`가 없으므로
`cmd && break`가 마지막 명령으로 실패해도 스크립트가 안 죽는다. 그래도 plan은
`if ... then break; fi`로 쓴다 — 나중에 누가 `-e`를 켤 때 이 함수가 원인이
되지 않게 하기 위함이다.

**2. 여섯 체인 전부 `cd "$(dirname "$0")"`으로 시작한다.** 그래서 `source`
경로가 `../gate_lib.sh` 하나로 고정된다.

**3. 다섯 체인의 `type_keys`는 글자 그대로 같다.** input(`:122`) ·
copy(`:108`) · render(`:104`) · config(`:70`) · power(`:108`)이고 본문이
동일하다. 함수 **위의 주석은 체인마다 다르다** — sendkey의 의미를 설명하는
내용이라 남긴다.

**4. `terminal/check.sh`에는 `type_keys`가 아예 없다.** 같은 일을 하는 인라인
`for` 루프가 둘 있다(`:131` "math 6 x 7" 10키, `:161` "exit" 5키).
**그리고 같은 파일 `:139`에 이미 폴링이 있다** — 결과를 고정 `sleep 3` 대신
`42`가 뜰 때까지 기다리도록 바꾼 자리이고, 이 milestone이 하려는 것과 같은
성격의 변경이다. **처방의 원형이 저장소 안에 이미 있다.**

**5. `config/check.sh`만 전역 `$LOG`가 없다.** 부팅이 둘이라 `LOG1`·`LOG2`를
쓰고, 타이핑하는 `edit_config_in_guest`는 `local log="$1"`로 받는다. 다섯
체인은 전역 `LOG`를 쓴다(input은 `LOG="$LOG1"`/`LOG="$LOG2"`로 갈아 끼운다).
**그래서 config만 한 줄이 더 필요하다.**

## 이번에 정하는 것 셋 (design doc이 안 정한 자리)

### 결정 1. 폴링 간격은 0.01초, 횟수는 25회다

0.05 + 0.01 × 25 = **0.3초**로, 최악의 경우가 지금 값과 정확히 같아진다.
"이 변경은 어떤 경우에도 지금보다 느려지지 않는다"를 산수로 보이는 것이 이
숫자를 고른 이유다.

**폴링마다 `wc -c`를 한 번 부르는 비용은 감수한다.** 최악 25회이지만, TCG
에뮬레이션에서 키 하나의 왕복이 수십 밀리초이므로 대개 첫 검사에서 끝난다.
`wc`가 정말로 비싸면 그것은 Task 1의 실측에서 드러난다.

### 결정 2. `$LOG`가 없으면 즉시 죽는 것을 그대로 둔다

체인들이 `set -u`이므로 `$LOG`가 없으면 `LOG: unbound variable`로 그 자리에서
죽는다. **막지 않는다** — 새 체인을 만들며 `$LOG`를 안 정한 사람에게 가장 빨리
알려주는 방법이고, GL-M0이 진입 검사로 막아야 했던 "조용히 통과한다"와는 종류가
다르다.

`source`를 빠뜨렸을 때도 마찬가지로 `type_keys: command not found`가 즉시 난다.
**둘 다 즉시 드러나므로 새 정적 검사를 만들지 않는다**(design 결정 7).

### 결정 3. copy 체인 하나를 먼저 옮겨서 재고, 그 뒤에 나머지를 옮긴다

Task 1이 `gate_lib.sh`를 만들고 **copy 체인만** 옮긴 뒤 단독으로 3연속 돌린다.
같은 체인의 앞뒤를 비교하면 루트 게이트보다 잡음이 작아 **절약이 먼저 갈린다.**
그리고 안전 쪽 위험(키를 놓친다)이 만약 있다면 여섯 체인이 아니라 한 체인에서
드러난다.

**copy를 고른 이유는 0.3초 키가 가장 많고(151) 종류도 가장 다양하기 때문이다** —
셸 타이핑 · copy mode 이동 · 검색 프롬프트 입력이 한 체인에 다 있다.

### Step 2: `gate_lib.sh`를 만든다 (사용자가 편집)

**새 파일** `gate_lib.sh`(저장소 루트). 넣을 것:

```bash
# 게이트 체인들이 함께 쓰는 타이핑 헬퍼.
#
# **왜 파일 하나인가.** GL-M2 전까지 아래 함수는 다섯 체인에 글자 그대로 같은
# 모양으로 다섯 벌 있었고, terminal 체인에는 같은 일을 하는 인라인 for 루프가
# 둘 더 있었다. 대기 방식을 바꾸려면 일곱 자리를 함께 고쳐야 하는데, 고친
# 것을 다시 일곱 벌로 두면 이 저장소가 이미 앓고 있는 병(로그 문구가 init
# 코드와 check.sh 양쪽에 있는 것)을 한 자리 더 만든다.
#
# 체인은 여전히 단독으로 실행할 수 있다. 같은 저장소 안의 파일이라 네트워크도
# 빌드도 필요 없고, 체인이 전부 `cd "$(dirname "$0")"`으로 시작하므로 경로가
# ../gate_lib.sh 하나로 고정된다.

# 게스트에 키를 한 개씩 보내고, **게스트가 반응할 때까지** 기다린다.
#
# 부르는 쪽이 갖춰야 하는 것 둘:
#   fd 3    QEMU monitor에 연결돼 있어야 한다
#   $LOG    그 부팅의 시리얼 로그 파일 경로
# 둘 중 하나라도 없으면 그 자리에서 죽는다(체인들이 set -u다). 막지 않는
# 것이 의도다 — 빠뜨린 사람에게 가장 빨리 알려준다.
#
# **왜 고정 sleep이 아닌가.** GL-M2 전에는 키마다 0.3초를 무조건 쉬었다.
# 그 0.3은 "이만하면 충분할 것이다"라는 짐작이고, 짐작이 틀리는 날의 증상은
# 게이트가 가끔 깨지는 것이다. 로그가 자라는 것을 보면 짐작이 사라진다.
#
# **왜 문자열이 아니라 파일 크기인가.** 어느 줄이 찍히는지는 키마다 다르다 —
# 셸로 가는 글자는 에코를 거쳐 screen>을, copy 명령은 copy>를, 검색 프롬프트
# 안의 글자는 find> type을 만든다. 어느 줄인지 알 필요 없이 "무언가 반응했다"
# 만 알면 되므로 크기를 본다.
#
# **이 판정이 서는 이유는 로그가 조용하기 때문이다.** main.zig의 렌더가
# needs_redraw를 문지기로 두고 있어서(TR-M2) 아무 일도 없으면 프레임이 안
# 찍힌다. **그 성질을 깨는 사람은 이 함수도 함께 봐야 한다.**
#
# 아래 한도 0.05초는 CM-M0의 실측이다 — 0.05초 간격으로 80번을 보내도 하나도
# 안 떨어진다. 위 한도는 0.05 + 0.01 × 25 = 0.3초이고 GL-M2 전의 값과 같다:
# **로그를 한 글자도 안 만드는 키가 있어도 이 변경이 지금보다 느려지지 않는다.**
type_keys() {
  local k before i
  for k in "$@"; do
    before="$(wc -c < "$LOG")"
    echo "sendkey $k" >&3
    sleep 0.05
    for i in $(seq 1 25); do
      if [ "$(wc -c < "$LOG")" -gt "$before" ]; then break; fi
      sleep 0.01
    done
  done
}
```

### Step 4: 다시 잰다 (Claude가 실행, 약 4분)

Step 1과 **같은 명령**을 돌린다. 통과와 시간을 함께 본다.

**볼 것 셋.**

1. `exit=0`인가. 키를 놓쳤으면 검사 열여덟 중 하나가 죽는다.
2. 시간이 얼마나 줄었는가. 예상은 회차당 45.3초 × 3 = 2분 16초 중 대부분이다.
3. **`terminal: key>` 줄 수가 앞뒤로 같은가.** 키가 덜 도착했는지를 시간이
   아니라 개수로 본다.

   **그 줄은 체인 stdout에 없다.** 체인이 시리얼 로그를 `mktemp` 파일에 담고
   통과하면 뿜지 않으므로, **같은 `docker run` 안에서** `/tmp/tmp.*`를 세야
   한다. `-a`를 반드시 붙인다(로그에 NUL이 있으면 `grep`이 binary로 취급한다).

   ```bash
   bash copy/check.sh > /tmp/copy.out 2>&1; echo "exit=$?"
   grep -ac 'terminal: key>' /tmp/tmp.*
   ```

> **Step 1 결과 (2026-08-28).** copy 체인 3연속이 **167초 · 167초 · 166초**,
> 셋 다 `CM-M2 check PASS`다. **폭이 1초라 앞뒤 비교가 아주 잘 선다** — 루트
> 게이트의 ±3분과 대비되는 자리이고, 결정 3이 체인 단독 측정을 먼저 두기로 한
> 근거가 여기서 확인됐다.
>
> 회차당 타이핑이 45.3초이므로 **167초의 27%**다. 바꾼 뒤 예상은 약 **132초**다.
>
> 데운 뒤의 산출물은 `terminal` 49,369,848바이트 · initrd 16,201,861바이트였다.

> **Step 4 결과 (2026-08-29).** copy 체인 3연속이 **143초 · 142초 · 139초**,
> 셋 다 `CM-M2 check PASS`다. **167·167·166초에서 회차당 25초(15%) 줄었다.**
> 앞뒤 여섯 값의 폭이 각각 1초와 4초라 이 차이는 잡음이 아니다.
>
> **키당 평균이 0.3초에서 약 0.135초가 됐다.** 아래 한도 0.05초를 뺀 0.085초가
> 게스트가 실제로 반응하는 데 걸리는 시간이다 — 폴링 간격이 0.01초이므로 여덟
> 번에서 아홉 번째 검사에서 통과한다는 뜻이고, **그만큼은 줄일 수 있는 시간이
> 아니라 기다려야 하는 시간이다.**
>
> **그래서 게이트 예상을 낮춘다.** 회차당 147.6초가 약 66초가 되어 회차당
> 81초, 3회차에 4분 03초를 던다. 22분 19초~35초 → **약 18분 20초**다.
> design에 적은 16분 45초는 키당 0.07초를 가정한 값이라 낙관이었다.

> **`key>` 줄 수는 키 개수가 아니다 — 이 milestone이 실행으로 알아낸 것.**
> 세 회차가 78 · 82 · 71로 흔들렸는데 검사는 전부 통과했다. `readKeys`가 한
> 번의 `read()`에 여러 키를 실어 오면 `main.zig`가 `key> 3 byte(s)`처럼 **한
> 줄로** 찍기 때문이다. **타이핑이 빨라지면 배칭이 늘어 줄 수가 오히려 준다.**
>
> 그래서 "키를 놓쳤는가"는 줄이 아니라 **바이트 합**으로 본다.
>
> ```bash
> grep -aoE 'key> [0-9]+ byte' /tmp/tmp.* | awk '{s+=$2} END {print s}'
> ```
>
> **`copy/check.sh`의 `key_lines()`도 같은 성질을 갖는다.** 그 함수는 값의
> **변화 여부**만 보는 음성 검사에 쓰이므로 지금까지 문제가 없었지만,
> 절대값으로 키 개수를 세려는 사람은 여기서 틀린다.
>
> **그 바이트 합으로 앞뒤를 직접 대조했다.** 바꾸기 전 `check.sh`를
> `git show HEAD:copy/check.sh`로 꺼내 마운트해서 한 회차, 바꾼 뒤로 한 회차를
> 같은 컨테이너 조건에서 돌렸다.
>
> | | `key>` 줄 수 | **바이트 합** |
> |---|---|---|
> | BEFORE | 95 | **95** |
> | AFTER | 78 | **95** |
>
> **키를 하나도 안 놓쳤다.** 그리고 배칭 해석이 같은 표에서 확정된다 —
> 0.3초 간격에서는 줄 수와 바이트 합이 같아 키 하나가 줄 하나였는데,
> 0.135초에서는 78줄이 같은 95바이트를 나른다.

## 실패했을 때 어디를 보는가

**게이트가 깨지면 먼저 "키가 덜 갔는가"와 "화면이 안 가라앉았는가"를 가른다.**
전자는 `terminal: key>` 줄 수가 줄어든 것으로 보이고, 후자는 줄 수는 같은데
검사가 본 값이 다른 것으로 보인다.

- **키가 덜 갔으면** 아래 한도 0.05초가 부족한 것이다. CM-M0의 실측은 copy
  mode의 방향키였고 셸 타이핑은 다를 수 있다 — 이것이 GL이 이 항목을 미뤘던
  바로 그 걱정이다. 그때는 아래 한도만 0.1초로 올린다.
- **화면이 안 가라앉았으면** 타이핑이 빨라져서 검사가 중간 상태를 본 것이다.
  그 검사에 폴링이나 `sleep`을 따로 붙인다. **`type_keys`를 되돌리지 않는다** —
  타이핑 대기와 화면 안정 대기는 다른 것이고, 지금 하나로 겸하고 있던 것을
  가르는 것이 오히려 옳다.
