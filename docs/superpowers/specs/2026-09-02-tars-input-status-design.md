# TARS Input Status — Design

Date: 2026-09-02
Status: 완료(IS-M0 2026-09-02 · IS-M1 2026-09-09). 상태 줄이 아래
여백에 뜨고 칸이 넷이다(한/영 · 한글 자판 · 영문 자판 · `CAPS`).
`Action.hangul`이 `Action.redraw`가 되어 긴 CapsLock이 그 자리에서 화면을
다시 그린다. 게이트 아홉 체인 3/3으로 18분 32.80초. plan은
`docs/superpowers/plans/2026-09-02-tars-input-status-is-m0.md`와
`.../2026-09-08-tars-input-status-is-m1.md`이고, 값은 아래 "IS-M0이 실측한
것"·"IS-M1이 실측한 것" 절에 있다.

Hangul Input(HI-M0~M3, 2026-08-31·09-01)이 남긴 비목표 넷 중 하나를 집는다 —
"입력기 상태를 화면에 보여 주기"다. HI의 design이 그것을 이렇게 적어
뒀다: "대문자 잠금에 LED도 표시도 없어서 켜 놓은 것을 잊으면 대문자가
나오는 것으로만 안다."

## 한 줄 요약

화면 맨 아래 여백에 상태 줄 하나를 그린다. 지금 한/영 중 어느 쪽인지,
어느 자판을 쓰는지, 대문자 잠금이 켜져 있는지를 한 줄로 보여 준다. 격자
바깥이라 터미널 47줄을 한 줄도 안 뺏는다.

```
  한  신세벌 PCS  쿼티  CAPS
```

## 왜 지금인가

HI가 전환 키를 넷 실었다 — 한/영 키 · Shift+Space · 짧은 CapsLock · 짧은 왼쪽
Ctrl. 켜는 길이 넷인데 지금 상태를 보는 길이 하나도 없다. 한글일 때만
조합 중인 글자가 뜨는 것이 유일한 신호이고, 그것은 자모를 하나 친 뒤에야
나온다.

대문자 잠금은 더 나쁘다. 긴 CapsLock이 그것을 뒤집는데 LED도 표시도
없다(TARS는 키보드 LED를 안 만진다). 켜 놓은 것을 잊으면 대문자가 나오는
것으로만 알고, 그때는 이미 친 뒤다.

## 배치 — 아래 여백 28픽셀

프레임버퍼가 1280×800이고 `GRID_X`·`GRID_Y`가 20, `CELL_W`가 8,
`ROW_HEIGHT`가 16이다. 그래서 `cols`가 155, `rows`가 47이고 격자는 y=20부터
772까지를 쓴다.

```
격자 아래 끝 = GRID_Y + rows * ROW_HEIGHT = 20 + 47*16 = 772
아래 여백    = fb.height - 772            = 28
글자 줄의 y  = 772 + (28 - 16) / 2        = 778
```

아래 여백 28픽셀은 지금 `fill(MARGIN_COLOR)`이 통째로 칠하고 마는
자리다(RC-M0이 잰 여백 91,520픽셀의 일부). `ROW_HEIGHT`가 16이라 글자 한
줄이 그대로 들어간다.

후보 넷 중 이것을 골랐다.

| 후보 | 왜 아닌가 |
|---|---|
| 맨 아랫줄 오른쪽 끝 | 검색 프롬프트와 같은 줄이다. 항상 떠 있으려면 터미널 47줄 중 한 줄을 영영 덮어쓴다. 검색어가 길면 겹친다 |
| 변할 때만 잠깐 뜨는 배지 | "지금 켜져 있는 것을 잊었다"는 원래 문제를 안 푼다. 시간 기반이라 게이트로 보기도 어렵다 |
| 위 여백 20픽셀 | 16픽셀 글자에 여백 4가 남아 빡빡하고, 시선은 보통 프롬프트가 있는 아래쪽에 있다 |
| 아래 여백 28픽셀 | 터미널 줄을 안 뺏고 `cells()`·`rows`·PTY 크기·검색 프롬프트와 아무 데서도 안 부딪힌다 |

## 결정

### 결정 1 — `vt.zig`는 한 줄도 안 건드린다

상태 줄은 터미널 화면의 내용이 아니라 우리가 화면 밖에 얹는 것이고,
`vt.zig`는 라이브러리가 주는 격자만 다룬다.

HI-M1이 preedit을 `vt.zig`에 넣은 것과 반대 방향인데 이유가 있다.
preedit은 커서 자리의 셀을 갈아 끼우는 일이라 격자 안이었다. 상태 줄은 격자
밖이고, `cells()`가 돌려주는 목록에 들어갈 자리 자체가 없다.

### 결정 2 — 칸이 넷이고 자리가 고정이다

| 칸 | 켜짐 | 꺼짐 |
|---|---|---|
| 1 | `한` | `EN` |
| 2 | `신세벌 PCS` · `공세벌 3-P3` · `신세벌 P2` · `두벌식` | — (항상 하나) |
| 3 | `쿼티` · `드보락` | — (항상 하나) |
| 4 | `CAPS` (밝게) | `CAPS` (어둡게) |

상태가 바뀌어도 칸이 사라지거나 밀리지 않는다. 사람이 매번 같은 자리를
보면 되고, 게이트도 "칸 개수"라는 판정을 하나 더 갖는다.

"켜졌을 때만 나타남"을 안 고른 이유가 이것이다 — 문자열 길이가 수시로
바뀌면 눈도 게이트도 어렵다.

넷 중 변하는 것은 둘뿐이다. `hangul_on`과 `caps_lock`은 키가 뒤집고,
`hangul_layout`과 `latin_layout`은 부팅 내내 상수다(`tars.conf`가 정한다).
자판 둘은 상태가 아니라 설정 읽어 주기이고, "내가 어느 자판을 켜 놨더라"에
답한다.

### 결정 3 — 4번 칸은 글자를 안 바꾸고 색만 바꾼다

`CAPS`와 `caps`는 흘깃 봐서 같아 보인다. 자리를 유지한 채 밝기로 가르는 편이
훨씬 잘 읽히고, 게이트는 색을 이미 잘 본다(`style>` 덤프가 하는 일이
그것이다).

### 결정 4 — 자판 이름은 예쁜 이름으로 쓰고, 표는 `else` 없는 `switch`로 만든다

`@tagName`이 주는 것은 `shin_pcs`·`sebeol_3p3`·`dubeol`·`shin_p2`이고
`qwerty`·`dvorak`이다. 사용자가 예쁜 이름을 골랐다 — `신세벌 PCS` ·
`공세벌 3-P3` · `신세벌 P2` · `두벌식` · `쿼티` · `드보락`.

그러면 enum → 표시 이름 표가 하나 늘고, 그것이 HI-M2 실측 6이 짚은
위험이다: "이 위험은 '표를 옮긴다'가 아니라 '사람이 읽고 다시 적는다'에
딸려 있었다."

처방은 `else`를 안 다는 것이다.

```zig
fn hangulName(l: hangul.Layout) []const u8 {
    return switch (l) {
        .dubeol => "두벌식",
        .sebeol_3p3 => "공세벌 3-P3",
        .shin_p2 => "신세벌 P2",
        .shin_pcs => "신세벌 PCS",
    };
}
```

배열이나 map으로 만들면 자판을 다섯째로 더하는 사람이 표를 빼먹어도 컴파일이
통과하고, 증상은 화면에 빈 칸이 뜨거나 엉뚱한 이름이 뜨는 것이다.
`else` 없는 `switch`는 그 순간 컴파일 에러를 낸다. 자판 이름은 이 저장소가
이미 `comptime` 앵커로 지키는 종류의 것인데(HI-M0 실측 7), 여기서는 언어가
공짜로 해 준다.

### 결정 5 — 글자 만들기는 새 모듈 `terminal/src/status.zig`로 뺀다

근거가 실측에 있다. SP-M1 실측 5 — "`promptText`가 `main.zig`의 private이라
`vt_test`가 못 부른다." `statusText`를 `main.zig`에 두면 정확히 같은 벽에
부딪히고, 호스트 검사가 자판 여섯 × 한/영 둘 × CapsLock 둘을 못 돈다.

`hangul.zig`가 선 자리와 같게 만든다 — 시스템 콜도 프레임버퍼도 `vt.zig`도
안 보는 순수 모듈이고, `main.zig`와 `status_test.zig`가 함께 import한다.
`main.zig`가 900줄을 넘긴 것도 이 결정을 거든다.

계약은 `statusText(state, buf) []const u8` 하나다.

버퍼는 36바이트면 충분하다. 가장 긴 줄이 `한`(3) + 두 칸 +
`공세벌 3-P3`(14) + 두 칸 + `드보락`(9) + 두 칸 + `CAPS`(4) = 36이다.
`promptText`의 173바이트와 같은 방식으로 주석에 산수를 남긴다.

여기는 `promptText`와 달리 값의 집합이 닫혀 있다 — needle 같은 가변
입력이 없고 자판 이름이 여섯, 한/영이 둘, `CAPS`가 하나다. 그래서 크기를
`comptime`에 이름 표에서 직접 계산할 수 있고, 자판을 더하는 사람이 버퍼를
같이 안 늘려도 컴파일러가 잡는다. 결정 4의 `switch`와 같은 종류의 못이다.

### 결정 6 — `drawPrompt`를 재사용하지 않는다

`drawPrompt`는 ASCII만 가정한다.

```zig
for (text) |ch| {                    // ← 바이트 하나 = 글자 하나
    const glyph = try cache.find(ch);
    drawGlyph(fb, glyph, GRID_X + col * CELL_W, y, fg);
    col += 1;                        // ← 언제나 한 칸
}
```

검색 needle이 지금 ASCII뿐이라(`Copy.find_char`가 `u8` 하나다 — HI가 남긴
이월 숙제) 여태 안 드러났을 뿐이다. 여기에 `한`을 넣으면 UTF-8 세 바이트가
글리프 셋으로 그려지고 자리도 세 칸을 먹는다.

`drawStatus`는 둘을 더 한다.

1. UTF-8을 디코드해서 코드포인트로 돈다 (`std.unicode.Utf8View`).
2. 폭 2 글자는 두 칸을 전진한다 — `col += glyph.cell_width / CELL_W`.
   `render()`가 격자에서 col을 쓰는 것과 같은 규칙인데, 거기는 라이브러리가
   spacer로 col을 미리 맞춰 줬고 여기는 우리가 센다.

여백이 `ROW_HEIGHT`보다 좁으면 아무것도 안 그린다. 지금은 28 ≥ 16이라
들어가지만, 높이가 다른 화면에서는 `rows`가 여백을 다 먹어 0이 될 수 있다.
그때 그리면 격자 바깥이 아니라 화면 밖에 쓴다.

### 결정 7 — 색은 셋이고, 앰버는 재사용이다

| 상수 | 값 | 어디 |
|---|---|---|
| `STATUS_FG` | `0x00808890` | 칸 1~3. 여백 위에서 읽히되 눈을 안 끄는 회색 |
| `STATUS_ON` | `0x00C08000` | `CAPS` 켜짐. SP-M0의 `CURRENT_BG`와 같은 값 |
| `STATUS_OFF` | `0x00303840` | `CAPS` 꺼짐. 여백(`0x00102030`)보다 조금 밝아 자리는 보이되 안 읽힌다 |

앰버를 재사용하는 데 뜻이 있다 — 이 저장소는 이미 그 색으로 "지금 봐야 할
것"을 뜻한다(현재 매치). 대문자 잠금이 켜진 것이 정확히 그런 것이다.

배경 띠는 안 깐다. `render()`가 이미 `fill(MARGIN_COLOR)`로 여백을 칠하고
시작하므로 글자를 그 위에 바로 찍으면 된다. 띠를 깔면 상태 줄이 터미널
내용처럼 보이는데, 이것은 내용이 아니라 창틀이다.

### 결정 8 — `Action.hangul`을 `Action.redraw`로 이름을 바꾼다

여기에 이미 구멍이 하나 있다. `input.zig:1139`다.

```zig
c.KEY_CAPSLOCK => {
    if (value == 0) {
        const tapped = self.caps_tap.up(time_us);
        if (tapped and self.toggles.capslock_tap)
            return self.toggleHangul();   // ← `.hangul` → 다시 그린다
        self.caps_lock = !self.caps_lock; // ← 상태만 바꾸고
    } else {
        self.caps_tap.down(time_us);
    }
    return nothing;                       // ← 아무것도 안 돌려준다 → 안 그린다
},
```

지금은 이것이 버그가 아니다 — 대문자 잠금은 다음에 치는 글자에서만
드러나고 그 글자가 어차피 다시 그린다. 그런데 상태 줄이 생기는 순간 버그가
된다: CapsLock을 켰는데 `CAPS`가 안 밝아지고, 아무 키나 하나 치면 그제야
밝아진다.

HI-M1 실측 2와 정확히 같은 함정이다 — "`Action.hangul`은 payload가 없는데
그것이 없으면 화면이 안 갱신된다. 자모 키는 PTY로 아무것도 안 보내고 스크롤도
copy 명령도 안 만들어서 `needs_redraw`가 안 켜진다." 이번에는 자모 키가 아니라
CapsLock이고 원인은 같다.

처방은 이름을 넓히는 것이다. `.hangul`의 뜻은 원래부터 "한글"이 아니라
"화면을 다시 그려라"였다(HI-M1이 주석에 그렇게 적어 뒀다). 한글이 아닌
두 번째 호출자가 생겼다는 것은 이름이 좁았다는 신호다. `Keys.hangul`도
`Keys.redraw`가 되고, 자리는 열넷인데 전부 컴파일러가 잡는다.

`Action.caps`를 새로 더하는 쪽을 안 골랐다. 더 작은 변경이지만 셋째
호출자가 생기면 `main.zig`가 `if (keys.hangul or keys.caps)`가 되고, 그
조건에 넷째를 빼먹는 것이 다음 사고다. 증상이 조용한 종류라서 그렇다 —
"안 그려진다"가 아니라 "가끔 늦게 그려진다"로 나타나고, 그것은 원인에서
아주 먼 증상이다(HI-M3 실측 4가 같은 말을 modifier switch에 대해 했다).

### 결정 9 — 로그는 값이 바뀌었을 때만 찍는다

RC-M0 실측 7이 시리얼 한 줄에 0.6~8.8밀리초라고 쟀다. 프레임이 21밀리초인데
`status>` 두 줄을 매 프레임 찍으면 최악 18밀리초가 붙는다.

그래서 마지막으로 찍은 값을 기억하고 바뀌었을 때만 찍는다. ink 스캔도 같은
조건에서만 돈다. 덤으로 로그가 읽기 좋아진다 — 한 줄이 곧 한 번의 전환이다.
첫 프레임은 기준선으로 반드시 찍는다(기억한 값이 없는 상태로 시작한다).

## 검증

### 호스트 검사 — `status_test` (`zig build test`)

| 검사 | 무엇 |
|---|---|
| 자판 이름 여섯 | 한글 넷 + 라틴 둘이 각각 맞는 이름을 낸다 |
| 한/영 둘 | `hangul_on`이 `한`/`EN`을 가른다 |
| CapsLock 둘 | 글자는 안 바뀌고 색만 바뀐다 |
| 칸 개수 | 상태가 무엇이든 칸이 넷이다 |
| 가장 긴 줄 | `공세벌 3-P3` + `드보락` + 나머지가 36바이트 버퍼에 들어간다 |

### 게이트 — `hangul/check.sh`에 판정 셋. 키를 하나도 안 더한다

`hangul/check.sh`가 이미 필요한 것을 전부 누른다. 한/영을 전환하고(검사
3~11), HI-M3이 넣은 `hold_key caps_lock`이 대문자 잠금을 켠다(검사 12~16).
그 자리마다 판정을 하나씩 얹는다. SP-M0이 검사 15에 `col` 판정 둘을 더할 때
쓴 방법과 같다 — 이미 찍히는 줄에서 값을 하나 더 읽을 뿐이다.

새 로그 줄 둘.

```
terminal: status> text=EN  공세벌 3-P3  쿼티  CAPS
terminal: status> caps ink on=0 off=37
```

| 언제 | 기대 |
|---|---|
| 부팅 직후 | `text=EN  공세벌 3-P3  쿼티  CAPS` · `on=0 off>0` |
| 한/영 전환 뒤 | `text=한  …` (자판 칸은 안 흔들린다) |
| 긴 CapsLock 뒤 | `on>0 off=0` — 키 하나 더 안 치고 바로 |

둘째 줄이 이 설계에서 가장 중요하다. 여백은 격자 밖이라
`screen>`·`style>`·`ink>`가 하나도 못 본다 — 첫째 줄만 있으면 `statusText`가
만든 문자열을 되읽는 것뿐이고, "글자는 만들었는데 화면에 안 그렸다"를 못
잡는다. 그래서 `present()` 뒤에 `CAPS` 칸의 픽셀을 `getPixel`로 직접 세어
`STATUS_ON`과 `STATUS_OFF`의 개수를 찍는다. `dumpInk`가 쓰는 방법 그대로다.

2026-09-02의 사고(실측 5)가 이 줄의 모양을 정했다. 그날 새 `ink` 판정이
`INK_DUMP_LIMIT` 여덟 개 제한에 걸려 커서와 무관한 글자를 보고 통과했다.
그래서 이 줄은 목록이 아니라 `CAPS` 칸의 x 범위 하나만 보는 전용 판정이고,
상한도 없다.

자판 칸이 `공세벌 3-P3`인 것이 판정의 절반이다. 기본값이 `신세벌 PCS`인데
게이트 디스크가 `sebeol_3p3`을 심으므로, 설정을 통째로 무시하는 코드는
여기서 갈린다(HI-M2 실측 10과 같은 규율).

마지막 줄의 "키 하나 더 안 치고 바로"가 결정 8의 구멍을 보는 유일한
자리다. `Action.redraw`를 안 만들었다면 CapsLock을 뗀 직후에는 아직 `off`가
나오고, 그다음 키에서야 `on`이 된다.

## Milestone

### IS-M0 — 상태 줄이 뜬다 (칸 셋)

`status.zig`(글자 만들기) · `status_test.zig`(호스트 검사) · `main.zig`의
`drawStatus`(그리기) · `status>` 첫 줄 · `hangul/check.sh`의 판정 둘(부팅
직후 · 한/영 전환 뒤).

갱신은 기존 경로만 쓴다. `Action.hangul`이 이미 `needs_redraw`를 켜므로
한/영 칸은 저절로 맞고, 자판 칸은 부팅 내내 상수라 갱신이 필요 없다.
새 경로를 하나도 안 만드는 것이 요점이다.

Exit gate: `zig build test` 통과 + 아홉 체인 3/3, 그중 `hangul/check.sh`의
새 판정 둘이 통과.

### IS-M1 — CapsLock 칸과 갱신 구멍

`Action.hangul` → `Action.redraw` 이름 바꾸기(자리 열넷) · CapsLock 분기에서
그것을 돌려주기 · 색 셋 · `status>` 둘째 줄(ink) · 게이트 판정 하나(긴
CapsLock 뒤).

Exit gate: 위와 같고, 새 판정 하나가 더 통과.

둘로 가르는 이유는 이 저장소가 여러 번 값을 본 그것이다(HI-M0 실측 8 ·
HI-M2 실측 4). M0이 증명된 갱신 경로만 쓰고 M1이 새 경로 하나를
넣으므로, M1에서 `CAPS`가 안 밝아지면 그리는 층을 의심할 필요가 없다 —
M0이 이미 그것을 초록으로 만들어 놨다.

## 위험

1. 로그 두 줄을 매 프레임 찍으면 렌더가 느려진다. 결정 9가 처방이다.

2. `drawPrompt`가 ASCII만 안다는 것을 잊고 재사용하는 것. 결정 6이다.
증상이 지독하다 — `한`이 글리프 셋으로 그려지고 뒤 칸이 전부 두 칸씩
밀린다.

3. 자판 이름 표를 빼먹는 것. 결정 4가 컴파일 시각에 막는다.

4. 폰트 캐시에 없는 글자. `공세벌 3-P3` 같은 한글이 처음 화면에 뜰 때 그
자리에서 래스터라이징이 일어난다. TR-M1부터 정상 경로이고 한 자당 밀리초
이하이며 같은 글자는 한 번뿐이다 — 첫 프레임에만 조금 늦는다.
`render> first frame` 값이 이것을 보여 줄 것이고, 착수 전 기준선과 비교한다.

## IS-M0이 실측한 것

1. `MAX_LEN`이 정확히 30으로 계산됐다. 검사 10이 "가장 긴 줄의 길이가
`MAX_LEN`과 같다"를 보는데(크거나 같다가 아니다) 첫 시도에 통과했다 —
`한`(3) + 공백 둘 + `공세벌 3-P3`(14) + 공백 둘 + `드보락`(9)이라는 plan의
산수가 이름 표의 실제 바이트 수와 어긋나지 않았다는 뜻이다. `comptime`에
세게 한 것이 값을 한 자리는 아직 오지 않는다 — 자판을 다섯째로 더하는
사람이 버퍼를 손으로 안 늘려도 되는 것이 그 값이고, IS-M1이 `CAPS` 여섯을
더할 때 처음 확인된다.

2. `status> ink fg=`가 383이고 세 번의 게이트 회전에서 값이 같았다.
한/영을 켜면 381이 된다(`EN` 두 글자와 `한` 한 글자의 획 수 차이다).
이 값이 이 milestone에서 "그렸다"를 증명하는 유일한 자리다 — 상태 줄은
격자 바깥이라 `screen>`·`style>`·`ink>`가 하나도 못 본다. 값이 0이었다면
`text=`는 맞는데 화면은 비어 있는 상태였고, `text=` 판정 둘만 뒀다면 그것을
못 잡았다.

3. "값이 바뀔 때만 찍는다"가 게이트 시간이 아니라 로그 자체로 증명됐다.
시리얼 로그에서 `screen>`이 57번인데 `status>`는 12줄이다 — 매 프레임
찍었다면 114줄(57×2)이었을 것이고, 12는 전환 여섯 번 × 두 줄이다.
게이트 시간은 이것을 보기에 너무 무딘 도구였다(19분 06.47초 대 직전
18분 43.9초로 +22.6초인데, HI-M2 실측 11이 잰 같은 세션 삼중값의 폭이
2.29초, 다른 날 잡음은 ±3분이다). plan은 "분 단위로 늘었다면"을 신호로
삼았는데, 줄 수를 직접 세는 쪽이 훨씬 곧다.

4. `render> first frame`을 echo하는 체인이 하나도 없다 — plan Step 2의
전제가 틀렸다. plan은 "값은 게이트 로그에 있다"고 적었지만 체인들은 시리얼
로그를 `mktemp` 파일에 두고 판정 결과만 echo한다. 값을 꺼내려면 시리얼
로그 자체가 필요하고, 파일을 하나도 안 고치고 꺼내는 길이 있다 —
`docker run -e TMPDIR=/workspace/out`으로 `mktemp`을 bind-mount된 디렉터리로
돌리면 된다. 체인의 `$LOG`를 호스트에서 읽어야 하는 다음 사람이 같은 것을
쓴다.

5. design이 적어 둔 첫 프레임 기준선(11~22밀리초)은 이 세션에서 안
맞았다 — 착수 전이 이미 27.9밀리초다. 그 값은 GL-M3 때 다른 날 잰
것이다. 같은 세션에서 착수 전 커밋(`f122931`)의 `main.zig`와 `check.sh`만
되돌려 다시 쟀다.

| | 첫 프레임 |
|---|---|
| 착수 전 (같은 세션) | 27,905µs |
| IS-M0 | 38,875µs |
| 차이 | +11.0밀리초 |

낡은 기준선과 비교했으면 +17~28밀리초로 보여 위험 4가 실현된 것처럼
읽혔을 것이다. HI-M2 실측 11("비교하려는 두 값은 같은 세션에서 재는 편이
훨씬 낫다")이 게이트 시간만이 아니라 문서에 적힌 모든 기준선에 걸린다.
각 한 번씩 잰 값이라 폭은 모른다.

6. 그 +11밀리초는 캐시가 다시 굽는 것이 아니다. 위험 4가 "수십 밀리초로
뛰었다면 캐시가 매 프레임 다시 굽고 있다는 뜻이고, 그때는 `cache.count()`
줄이 반복해서 찍힌다"고 처방을 함께 적어 뒀는데, 실제 로그의 캐시 개수는
11 → 19 → 21 → … → 38로 단조 증가하고 한 번도 안 줄어든다. 상태 줄의
한글 여덟 자가 첫 프레임에 한 번 구워지는 비용이고 부팅당 한 번이다.
증상이 같아 보이는 두 원인을 가르는 판정을 위험 항목에 함께 적어 둔 것이
값을 했다.

7. `build.zig`의 `test_step` 목록에서 `input_test`가 빠질 뻔했다.
Task 1 Step 2가 "`test_step.dependOn(&b.addRunArtifact(hangul_test).step);`를
지우고 두 줄로 바꾼다"는 모양이었는데, 그 줄과 똑같이 생긴 줄이 목록에 다섯
개 있어서 편집이 목록의 첫 줄(`input_test`)에 들어갔다. 결과는
`input_test`가 목록에서 사라지고 `hangul_test`가 두 번 등록된 것이다.
`zig build test`는 이 상태로도 초록이다 — 검사가 틀려서 빨개지는 것이
아니라 아예 안 도는 것이라, 못 봤으면 한글 층·전환 키·tap-vs-hold를 보는
검사 전부가 한 milestone 내내 잠들어 있었다. 잡은 것은 커밋 전
`git diff`이고(CC-M0의 규율), plan이 Task 1 Step 3에 "일부러 실패를
본다"를 둔 것도 같은 구멍을 겨눈 것이었다. `dependOn` 목록처럼 줄이
서로 구별되지 않는 자리는 지울 줄만으로 위치를 지정할 수 없다.

8. 게이트가 안 갈렸다. 아홉 체인 3/3으로 19분 06.47초, 직전
18분 43.9초에서 +22.6초다. 키를 하나도 안 더했고 새 로그 줄은 전환이 있을
때만 찍히므로 예상대로다.

## IS-M1이 실측한 것

1. "전부 컴파일러가 잡는다"는 참이지만 "한 번에 보여 준다"는 아니었다.
결정 8이 약속한 그것을 실제로 써먹으려고 선언 둘만 먼저 고치고 빌드했는데,
Zig가 `error: 3 compilation errors`로 셋까지만 보고하고 멈췄다. 자리가
열둘이었으므로 그대로 갔으면 네 번 왕복했을 것이다. plan이 미리 `rg`로
목록을 만들어 둔 덕에 한 번에 끝냈고, 컴파일러가 준 셋이 그 목록 안에
있다는 것이 목록이 맞다는 증거였다.

2. 컴파일러가 못 잡는 자리가 정확히 다섯이었고, 그중 하나를 실제로
놓쳤다. 지역 변수 `hangul_changed` 넷과 주석 하나(`input_test.zig:888`)다.
타입이 안 걸리므로 언어가 도와주지 않는다. 놓친 것은
`input.zig:1372`의 주석이었고 `rg`가 잡았다. 결정 8의 "자리 열넷"은
타입에 대한 셈이지 이름에 대한 셈이 아니다 — 이름까지 세면 열아홉이다.

3. plan이 편집 자리를 하나 빠뜨렸고, 잡은 것은 실행 중인 검사였다.
`input_test`에서 `KEY_CAPSLOCK`을 `value=0`으로 놓는 자리가 일곱인데
(짧은 tap 셋 · 긴 hold 넷), plan은 검사 번호로 훑다가 `cl_off`의 하나를
빠뜨렸다. 여기서도 타입이 같아 컴파일러가 못 잡는다.

4. "지울 것을 안 지우고 넣기만 한" 편집은 증상이 조용하다. 위의 자리를
고치면서 옛 줄이 남고 새 줄이 더해져 같은 시각에 같은 키를 두 번 뗐다 —
대문자 잠금이 두 번 뒤집혔다. 실패 메시지는
`code=58 -> got redraw, want bytes`라 "구현이 틀렸나"로 읽히지 "검사가
중복됐나"로는 안 읽힌다. `rg -n 'KEY_CAPSLOCK'`으로 자리를 세어 보고서야
두 줄이 같은 시각(`100_000`)을 가리키는 것이 보였다. IS-M0 실측 4의
사촌이고, 이번엔 지운 줄이 아니라 안 지운 줄이었다.

5. `MAX_LEN`이 손을 안 대고 30에서 36이 됐다. IS-M0 실측 1이 "그 값이
값을 하는 자리는 아직 오지 않았다"고 적어 둔 자리가 이것이다. `statusText`에
`GAP + CAPS`를 더하면서 `MAX_LEN`의 산수를 함께 고쳤을 뿐 버퍼 크기를
손으로 늘린 자리는 한 군데도 없고, 검사 10이 `>=`가 아니라 `==`로 보므로
산수와 이름 표가 어긋났으면 그 자리에서 갈렸다.

6. `on=87`과 `off=87`이 같다 — 그것이 결정 3의 직접 증거다. 같은 글리프
넉 자를 다른 색으로 칠했으니 획 픽셀 수가 같아야 한다. 하나라도 달랐다면
글자나 자리가 함께 바뀐 것이다. `ink fg=`는 383(영문)·381(한글)로 IS-M0이
잰 값 그대로다 — `CAPS`가 다른 색이라 앞 세 칸의 셈에 안 섞인다.

7. 수정을 꺼 놓고 게이트를 돌려 판정이 무엇을 보는지 확인했다.
2026-09-02의 규율(실측 5)을 그대로 따랐고, 이번에는 판정이 제 몫을 했다.

```
FAIL: a long CapsLock did not light the CAPS field (on=0); Action.redraw is missing
terminal: status> caps ink on=0 off=87
```

`off=87`이 함께 나온 것이 짝의 값이다 — "아예 안 그렸다"였다면 `off`도
0이었을 것이고, 이 값은 "안 그렸다"가 아니라 "안 밝아졌다"를 정확히
가리킨다. 두 색을 한 줄에 함께 찍기로 한 결정이 여기서 값을 했다.

8. 그런데 게이트를 밟으려면 호스트 검사부터 꺼야 했다. `return .redraw;`
한 줄만 죽였더니 체인이 부팅에 가지도 못하고 `input_test`에서 멈췄다.
`expectRedrawAt` 넷까지 함께 되돌리고서야 게이트 판정을 볼 수 있었다.
18분짜리가 보는 것을 초 단위로 답하는 층이 먼저 지키고 있다 — 검사를
어느 층에 둘지 정할 때 쓸 사실이다.

9. `status>`가 24줄이다. `screen>`이 59번이므로 매 프레임 찍었다면
177줄(59×3)이었을 것이고, 24는 전환 여덟 번 × 세 줄이다(한/영 여섯 +
대문자 잠금 둘). IS-M0 실측 3이 세운 방법을 그대로 썼다 — 줄이 둘에서
셋으로 늘었는데도 비율이 그대로인 것이 결정 9가 지켜졌다는 뜻이다.

10. 게이트가 안 갈렸다. 아홉 체인 3/3으로 18분 32.80초, 직전
19분 06.47초에서 34초 줄었다. 키를 하나도 안 더했으므로 예상대로이고,
줄어든 것도 늘어난 것과 마찬가지로 잡음이다.

11. 첫 프레임이 41,744µs로 IS-M0의 38,875µs에서 +2.9밀리초다.
`C`·`A`·`P`·`S` 넉 자가 첫 프레임에 새로 구워지는 비용이다(그 전까지 상태
줄에 대문자가 없었다). 각 한 번씩 잰 값이라 폭은 모른다 — IS-M0 실측 5가
경고한 그대로이므로, 다음에 이 값을 쓰는 사람은 같은 세션에서 다시 재는 편이
낫다.
