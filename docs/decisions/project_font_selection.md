# 폰트 후보 조사와 후보를 가르는 기준 (2026-08-23)

사용자의 로컬 기계(`~/Library/Fonts`)에 설치된 폰트 중 터미널에 쓸 만한
후보를 전부 재서 비교한 결과다. 계기는 사용자가 데스크톱 터미널에서 쓰는
**Monoplex Nerd**를 TARS에도 쓸 수 있는지 물은 것이었다.

## 후보를 가르는 것은 커버리지가 아니라 안티앨리어싱이다

TARS의 렌더러는 **문턱값 렌더링**을 쓴다(design 결정 4). `main.zig`의
`drawGlyph`가 `coverage > 127`이면 전경색을 찍고 아니면 안 찍는다. 중간값을
섞지 않는다. 게이트의 픽셀 검사가 정확한 상수와 비교할 수 있게 하려는
선택이기도 하다([[project_terminal_rendering]]).

그래서 **16픽셀에서 안티앨리어싱이 생기는 아웃라인 폰트는 그대로 넣으면
글자가 무너진다.** 샘플 `ABCgjq0189가한글놀ㄱㅏㅎㅣ은택─│┌`를 16픽셀로
구워 잉크 픽셀 중 중간값의 비율을 셌다.

| 폰트 | 크기 | ASCII | 음절 | 호환자모 | 조합용 자모 | 한자 | A/한 폭 | 중간값 비율 |
|---|---|---|---|---|---|---|---|---|
| **Hanme (현재)** | 441KB | 95/95 | 11172 | **0/51** | 18/20/26 | 0 | 8 / 16 | **0.0%** |
| **unifont 17.0.03** | 5197KB | 95/95 | 11172 | **51/51** | **19/21/27** | 20992 | 8 / 16 | **0.0%** |
| MonoplexNerd | 10039KB | 95/95 | 11172 | 51/51 | 0 | 12710 | 8 / 16 | 92.8% |
| MonoplexWideNerd | 10064KB | 95/95 | 11172 | 51/51 | 0 | 12710 | 9.6 / 16 | 92.8% |
| PlemolKRConsole | 9894KB | 95/95 | 11172 | 51/51 | 0 | 12710 | 8 / 16 | 92.8% |
| D2Coding | 8255KB | 95/95 | 11172 | 51/51 | 0 | 4620 | 8 / 16 | 81.3% |
| TubakDot | 932KB | 95/95 | 11172 | 51/51 | 0 | 4620 | 10 / 14.6 | 87.7% |

조합용 자모의 만점은 19 / 21 / 27이다. 중간값 비율 0%가 곧 비트맵 폰트라는
뜻이고, 문턱값 렌더링에 안전한 것은 **Hanme과 unifont 둘뿐이다.**

## Monoplex Nerd는 쓸 수 없다

호환 자모 51자를 전부 갖고 있어서 보고된 문제 자체는 해결한다. 그런데
아웃라인 폰트라 16픽셀에서 잉크의 **92.8%가 중간값**이고, 문턱값으로 자르면
획이 1픽셀로 끊기거나 사라져 `한`·`글`을 읽기 어려워진다. 파일도 10MB다.

**이 폰트를 쓰려면 `drm.zig`가 coverage를 배경색과 알파 블렌딩해야 하고,
그것은 design 결정 4를 뒤집는 일이다.** 게이트의 픽셀 검사가 상수 비교를
못 하게 되므로 검사 방식도 함께 바꿔야 한다. TR-M1의 범위가 아니다.

## unifont가 대안이다

GNU Unifont 17.0.03(`~/Library/Fonts/unifont-17.0.03.otf`)을 실측했다.

- `unitsPerEm`이 **64**라 16픽셀에서 `scale`이 정확히 0.25다. 16x16 픽셀
  격자를 그대로 담은 비트맵 폰트라 중간값이 하나도 없다.
- advance가 라틴 8픽셀, 한글 16픽셀로 **지금 격자(`CELL_W=8`,
  `ROW_HEIGHT=16`)와 정확히 같다.** 렌더러의 상수를 안 바꿔도 된다.
- 형식이 CFF(OpenType/PostScript)인데 **vendor된 `stb_truetype.h`가 문제없이
  읽는다.** 직접 컴파일해서 확인했다(`stbtt_InitFont` 성공, numGlyphs=58911).
- ASCII·호환 자모 51·조합용 자모 67·완성형 11172·박스 드로잉 128자를 16픽셀로
  전부 구워 봤을 때 **셀 밖으로 새는 글자가 하나도 없다**(11640자 검사, 위·아래·
  가로 넘침 0). `ascent=56`, `descent=-8`이라 `ascent_px`가 14다.
- 한자 20992자와 박스 드로잉 128/128을 함께 얻는다. Hanme은 한자가 0이고 박스
  드로잉이 40/128뿐이다.
- 라이선스는 **SIL OFL 1.1과 GNU GPL v2+ (Font Embedding Exception) 이중
  라이선스**라 재배포에 문제가 없다.

## 크기 부담은 재 보니 작다

값은 크기 하나뿐인데, 계산하면 반대 근거가 약해진다.

| | 원본 | gzip |
|---|---|---|
| **현재 initrd 전체** | 67.6MB | **15.5MB** |
| Hanme | 441KB | 95KB |
| unifont | 5197KB | 1278KB |

폰트는 `kernel/make_initrd.sh:94`가 initrd에 복사하고 `:188`이 `gzip -9`로
압축한다. 교체하면 압축된 initrd가 **15.5MB에서 약 16.7MB로 8% 늘어난다.**
커널이 `/init`에 넘기는 1.12초 중 51%인 0.57초가 압축 해제이므로
([[project_kernel_config]]) 늘어나는 시간은 **50밀리초 안팎**이다. initrd를
지배하는 것은 폰트가 아니라 셸과 유저랜드다.

## 선택지

| 안 | 내용 | 비용 |
|---|---|---|
| A | Hanme 유지 + 호환 자모를 조합용 자모로 대체하는 표 + 빠진 3자를 상수 비트맵으로 | 441KB 유지, Zig 약 80줄 |
| **B** | **unifont로 교체** | **gzip 기준 +1.2MB(8%), 부팅 +50ms, 우회 코드가 전부 불필요해짐** |
| C | unifont를 한자 없이 subset해서 교체 | B보다 1MB쯤 작고, 빌드에 `fontTools` 의존성과 subset 단계가 추가됨 |
| D | Monoplex Nerd 등 아웃라인 폰트 + 알파 블렌딩 | design 결정 4 반전, 게이트 픽셀 검사 재설계 |

## 추천은 B다 (2026-08-23)

> **사용자 결정(2026-08-23): 교체는 하되 TR-M1 다음이다.** TR-M1은 Hanme로
> 닫고 게이트까지 통과시킨 뒤, unifont 교체를 별도 작업으로 다룬다. 이 문서의
> 추천(B)은 그대로 유효하고, 착수 시점만 미뤄졌다.
>
> **미루는 비용이 애초 걱정보다 작았다.** 이 문서와 당시 `HANDOFF.md`는
> "TR-M1 Task 4가 `ink>` 기대값을 게이트에 적는 자리라 폰트를 나중에 바꾸면
> 그 값을 두 번 쓰게 된다"고 적었는데, **실제로 쓴 게이트는 정확한 값이 아니라
> 0인지만 본다**(`render/check.sh`의 `INK_LEFT -eq 0`). 나머지 검사도 폰트와
> 무관하다. **다시 써야 하는 곳은 `font_test.zig`의 기대값 표 다섯 줄뿐이다.**

1. **자모 우회로가 통째로 없어진다.** 대체 표도, 빠진 3자의 상수 비트맵도,
   낱자 재배치 보정도 안 쓴다. IME를 붙이는 날 폰트 쪽에서 할 일이 0이 된다.
2. **박스 드로잉이 40/128에서 128/128이 된다.** 지금은 TUI 프로그램의 테두리가
   군데군데 빈다.
3. **렌더러 코드를 한 줄도 안 고친다.** 격자와 문턱값 성질이 지금과 같다.

C를 권하지 않는 이유는 빌드에 Python 의존성이 붙는 대가로 얻는 것이 1MB
남짓이기 때문이다.

B로 갈 때 바뀌는 자리는 **여섯 곳이다**(2026-08-23에 다시 세었다 — 처음에
넷이라고 적었는데 `prepare.sh`의 주석과 sanity 프로그램을 빠뜨렸다).

```
terminal/vendor_fonts.sh             내려받는 URL과 파일 이름
kernel/make_initrd.sh:94             initrd에 복사
terminal/src/main.zig                경로 문자열
terminal/src/font_test.zig           경로 문자열 + 기대값 표 다섯 줄
terminal/prepare.sh                  주석
terminal/sanity/stb_truetype_main.c  경로 문자열
```

- **`ascent_px`는 안 고쳐도 된다.** 16에서 14로 바뀌지만 `font.zig`의
  `Cache.init`이 `stbtt_GetFontVMetrics`에서 읽는다.
- **`font_test.zig`의 기대값 표가 유일하게 "다시 재야" 하는 자리다.**
  `A`가 `7x10 y_offset=2`, `한`이 `15x15 x_offset=1 y_offset=0` 같은 값이
  전부 Hanme 실측이다. 셀 밖으로 새지 않는지 훑는 단언은 그대로 두면 되고,
  unifont는 11640자에서 넘침이 0이라는 것을 이미 확인했다.

**선행 작업이 하나 있다: 배포 URL을 확인해야 한다.** `vendor_fonts.sh`는
GitHub 릴리스에서 zip을 내려받는 구조인데, 위 실측은 사용자의
`~/Library/Fonts/unifont-17.0.03.otf`로 한 것이다. **게이트가 도는 컨테이너는
그 파일을 못 본다.** unifoundry.com 또는 GNU ftp의 안정적인 주소를 넣어야 한다.

## B를 실행했다 (2026-08-23) — 게이트 일곱 체인 3/3 통과

교체를 마쳤다. 예측이 맞은 것과 틀린 것을 나눠 적는다.

### 배포 URL은 GNU ftp에 있고, 사용자가 잰 파일과 바이트 단위로 같다

```
https://ftp.gnu.org/gnu/unifont/unifont-17.0.03/unifont-17.0.03.otf
26071c5a97533cefdcbc6b0645e7ee279413049079f09f592b26916ca6c21bf5
```

이 해시가 `~/Library/Fonts/unifont-17.0.03.otf`와 일치하므로 **위 표의
실측값을 다시 잴 필요가 없었다.** `vendor_fonts.sh`가 이 해시를 확인하고,
받다 만 파일이 최종 이름을 차지하지 않도록 `.tmp`에 받아서 옮긴다.

**저장하는 이름에는 버전을 넣지 않았다**(`vendor/fonts/unifont.otf`). 경로를
읽는 곳이 다섯 군데라 이름에 버전을 박으면 올릴 때마다 전부 고쳐야 한다.
버전은 `vendor_fonts.sh` 한 곳에만 있고, 어느 파일인지는 sha256이 보증한다.

### 바뀐 자리는 여섯이 아니라 **열**이었다

이 문서가 센 여섯에 더해 넷이 더 있었다. 앞의 셋은 `Hanme`이라는 낱말이
없어서 검색에 걸리지 않았다.

```
check.sh:10                   "8x4x4 폰트" 주석
terminal/build.zig:102        "vendor/fonts/*.ttf" 주석
terminal/src/font.zig         실측 주석 다섯 (코드는 한 줄도 안 바뀐다)
kernel/make_initrd.sh:186     initrd 크기 실측 주석
```

`font.zig`가 특히 그렇다. **코드는 폰트에 무관하게 옳았지만 주석이 Hanme의
숫자를 사실로 적어 두고 있었다** — `ascent=1600, unitsPerEm=1600`, `'A'가
-14`, `2.06MB에 29밀리초`. 고치지 않으면 다음 사람이 틀린 값을 믿는다.

### 예측이 틀린 것: `font_test`는 기대값 표만 바뀌지 않는다

이 문서와 HANDOFF가 "다시 재야 하는 곳은 기대값 표 다섯 줄뿐"이라고 적었는데
**4번 검사는 표본 자체가 폰트를 탄다.** 그 검사는 "그릴 것이 없는 글자는
에러가 아니라 빈 비트맵으로 오고 그래도 캐시에는 들어간다"를 보는데, 표본으로
U+4E00(한자)을 썼다. unifont에는 한자가 있다.

**표본을 바꾸는 것으로 끝나지 않는다. unifont에는 "폰트에 없는 글자"가
존재하지 않는다.** 일곱 후보를 시험했더니 전부 비트맵이 나왔다.

| 코드포인트 | Hanme | unifont |
|---|---|---|
| U+4E00 한자 | null | 15x1 |
| U+0378 미할당 | null | 14x14 |
| U+FFFF · U+E000 · U+1F600 · U+10000 · U+2FFFF | null | 전부 6x11 |

뒤의 다섯이 같은 크기인 것은 전부 `.notdef`로 떨어지기 때문이고, **unifont의
`.notdef`는 빈 글리프가 아니라 모양을 가진다.** 그래서 표본을 **공백**으로
바꿨다. 공백은 어느 폰트에나 있으면서 그릴 것이 없어서, `font.zig`가 적어 둔
"폰트에 없는 글자와 공백은 둘 다 null"이라는 계약을 폰트와 무관하게 확인한다.

**부수 효과가 하나 딸려 온다: 화면에 두부(tofu)가 뜨지 않는다.** 대신
`font.zig`의 "폰트에 없는 글자" 경로가 실질적으로 죽은 코드가 됐다.

### 예측이 맞은 것: 크기와 격자

| | 예측 | 실측 |
|---|---|---|
| gzip initrd | 16.7MB (+8%) | **16.76MB** (+8.1%) |
| cpio 원본 | — | 73.0MB (67.6MB에서) |
| 렌더러 코드 변경 | 없음 | **없음** (`CELL_W=8`·`ROW_HEIGHT=16` 그대로) |
| 셀 이탈 | 0 | **0** (ASCII·자모·박스·음절 11640자) |

`ascent_px`가 16에서 14로 줄었는데도 위로 새지 않는다. **unifont는 16x16
격자를 baseline 위 14px과 아래 2px로 나눠 쓰도록 설계된 폰트**이기 때문이다.
다만 여유가 0이다 — `font_test`가 재는 "가장 아래"가 Hanme의 15행에서
**정확히 16행**으로 올라갔다. 넘지는 않지만 1픽셀도 남지 않는다.

### 새 기대값 표 (unifont 17.0.03 실측)

```
A   6x10  cell_width=8   x_offset=1  y_offset=4
g   6x11  cell_width=8   x_offset=1  y_offset=5
한  15x14  cell_width=16  x_offset=1  y_offset=2
가  14x14  cell_width=16  x_offset=2  y_offset=2
é   6x12  cell_width=8   x_offset=1  y_offset=2
```

### 게이트

일곱 체인 전부 3/3. 렌더러가 보는 값 둘이 달라졌다.

```
terminal: ink> 3,0 U+D55C left=28 right=22     (Hanme: 39 / 25)
terminal: font> 31 glyph(s) cached, 1665 bytes  (Hanme: 1784 bytes)
```

**게이트가 흔들리지 않은 이유는 `ink>`를 상수와 비교하지 않고 좌우 절반이
0이 아닌지만 보기 때문이다.** TR-M1이 그렇게 쓴 것이 폰트 교체를 싸게 만들었다.
실사용 캐시가 **오히려 줄어든 것**도 눈여겨볼 만하다 — 파일은 12배 크지만
글리프 하나하나는 더 가늘다.
