게이트 자신의 정확성을 손본 서브프로젝트다. 기능을 더하지 않고, TARS를
판정하는 도구 안에서 종료 코드가 거짓이 되는 자리 일곱을 없앴다. 그리고
네 번째가 들어오지 못하게 루트 게이트의 진입 검사가 막게 했다.

design은 `docs/superpowers/specs/2026-09-12-tars-gate-accuracy-design.md`,
plan 둘은 `docs/superpowers/plans/`에 있다.

## 병

파이프라인의 뒤단이 조기 종료하면 앞단이 SIGPIPE로 죽고, 체인 맨 위의
`set -uo pipefail`이 그 141을 파이프라인 전체의 종료 코드로 올린다.
`grep -q`는 첫 매치에서 즉시 나가므로 그 조기 종료의 가장 흔한 원인이다.

141이 무엇이 되는지는 `if`의 모양이 정한다.

| 모양 | 증상 |
|---|---|
| `if ! … \| grep -q …; then fail` | 거짓 빨강 — 판정 글자가 로그에 있는데 빨갛다 |
| `if … \| grep -q …; then fail` | 거짓 초록 — 잡아야 할 것을 잡고도 통과한다 |

이 저장소가 같은 함정에 세 번 걸렸다. `tools/check.sh`(SM-M0) ·
`hangul/check.sh`(SM-M2) · 그리고 GA-M0이 고친 일곱. 세 번 모두 주석으로
경고를 적어 둔 뒤에 다시 밟았고, SM-M0은 그 경고를 쓴 파일 안에서 밟았다.

## 실측으로 드러난 것 — 다시 조사하지 말 것

### 임계는 파이프 버퍼 64KiB가 아니다

HANDOFF가 "로그가 파이프 버퍼(64KiB)보다 크면 터진다"고 적어 두었는데
틀렸다. 앞단 출력이 22,840바이트 — 버퍼의 3분의 1 — 일 때 이미 터진다.

| 앞단이 내는 바이트 | `918` 형 | `915` 형 |
|---|---|---|
| 5,710 | 0 / 200 | 0 / 200 |
| 22,840 | 63 / 200 | 160 / 200 |
| 68,520 | 199 / 200 | 200 / 200 |

앞단 `grep`이 출력을 한 번의 `write()`로 쏟지 않고 약 4KB 블록으로 나눠
쓰기 때문이다. 뒤단이 첫 블록 안의 매치에서 나가면 두 번째 블록의
`write()`가 이미 SIGPIPE를 받는다. 버퍼가 비어 있느냐는 상관이 없다 —
읽는 쪽이 닫혔으면 쓰는 순간 난다.

### 단일 임계값으로 말할 수 없다. 변수가 셋이다

같은 22,840바이트가 한 실험에서는 80%가 터지고 다른 실험에서는 19,454
바이트가 200/200 안전했다. 갈린 것은 앞단이 입력을 훑는 시간이다.

1. 앞단이 내는 출력량
2. 앞단이 입력을 훑는 시간 (로그 파일 전체 크기)
3. 뒤단이 나가는 지점 (매치가 앞쪽에 있는가)

"몇 바이트부터 위험하다"로 고칠 자리를 고를 수 없다는 뜻이다. 그래서
일곱을 전부 고쳤다.

### 검사가 망가지는 조건이 검사가 필요한 조건과 같을 수 있다

`config/check.sh:894`가 그 모양이었고 일곱 중 가장 나빴다. 평시에는 앞단
출력이 0줄이라 안전해 보인다 — 2차 부팅은 두 셸이 다 zsh라 fish 인사말이
없다. 그런데 시리얼 콘솔이 정말 fish로 떴다면(= 이 검사가 빨개져야 하는
상황) 화면 셸도 fish이므로 인사말이 `screen>` 프레임마다 붙어 앞단이 커진다.

| 화면 인사말 줄 수 | 앞단 바이트 | `-q` 쓴 코드가 FAIL을 말한 횟수 | `-q` 뺀 코드 |
|---|---|---|---|
| 200 | 19,454 | 200 / 200 | 200 / 200 |
| 1,000 | 97,054 | 0 / 200 | 200 / 200 |

평시 관측으로는 영영 안 드러나는 병이다. 음성 상황을 합성해서만 보인다.

### 앞단이 무엇을 거르는지가 위험을 정한다

`machine/check.sh`의 넷은 앞단이 71~267바이트뿐이고 구조적으로도
안전했다 — `_OSC`와 `keyboard device`는 부팅당 한 줄이라 로그가 자라도 줄
수가 안 자란다. `354`는 앞단이 자라지만 중간의 `tail -20`이 입력을 끝까지
읽고 20줄만 내보내므로 SIGPIPE를 받을 `tail`에게 267바이트밖에 안 간다.

그래도 고쳤다. 앞단의 패턴은 자라기 때문이다 — SC-M0이
`tars-init: config …` 한 줄에 여섯째 필드를 붙였을 때 `hangul` 체인이 그
줄 끝에 매달려 있다가 깨진 전례가 있다.

## 처방

`-q`를 빼고 출력을 `/dev/null`로 버린다. 뒤단이 입력을 끝까지 읽으므로
앞단이 SIGPIPE를 안 받고, 종료 코드만 쓰므로 출력은 필요 없다.

```bash
# 전
if ! grep -a "tars-init: keyboard device" "$LOG" | grep -aq "USB Keyboard"; then
# 후
if ! grep -a "tars-init: keyboard device" "$LOG" | grep -a "USB Keyboard" >/dev/null; then
```

`cat`을 끼우거나 `|| true`를 붙이는 것은 안 된다 — 종료 코드를 가려서 검사
자체를 무력화한다. `fail()`의 `|| true`는 출력용이라 괜찮았지만 판정
자리에서는 다르다.

## 재발 방지는 `check.sh`의 진입 검사에 있다

`require_no_early_exit_pipe`가 `require_build_steps` 옆에 있고, 같은
`CHAINS` 배열을 훑는다. 대상은 체인 열하나에 `gate_lib.sh`와 `check.sh`
자신을 더한 열셋이다. 부팅 전에 끝나므로 28분을 기다린 뒤가 아니라 시작
몇 초 안에 말해 준다.

주의할 것 둘.

1. `grep -n`을 먼저 걸고 주석을 나중에 거른다. 순서를 뒤집으면 줄 번호가
   원본과 어긋나 고칠 자리를 못 가리킨다. `require_build_steps`가 반대
   순서여도 괜찮았던 것은 그 검사가 번호를 안 쓰기 때문이다.
2. 패턴을 좁게 쓰면 못 찾는다. SM-M0의 `\| *grep -[a-z]*q`는 플래그 끝이
   `q`인 것만 찾아 `-aqE`를 놓쳤다. 지금 패턴은
   `\|[^|]*\b(grep|rg)\b[^|]*-[a-zA-Z]*q`이고 `q`가 플래그 가운데 있어도
   잡는다. `--quiet`와 `rg -q`도 잡힌다.

`check.sh` 자신을 대상에 넣은 이유는, 넣어 두면 미래에 패턴을 고쳐 자기가
자기에게 걸리는 순간 게이트가 즉시 빨개지고, 빼 두면 그 파일에 새로
들어오는 파이프라인을 아무도 안 보기 때문이다. 조용한 쪽보다 시끄러운
쪽이 낫다는 것이 이 서브프로젝트 전체의 주제다.

## lint의 음성 확인이 필수다

잡는 것 다섯과 안 잡아야 하는 것 넷을 함께 본다. 이 검사 자신이
아무것도 안 보는 검사가 되는 것을 막는 유일한 방법이고, `feedback` 아닌
쪽의 같은 함정이 SP-M0에 있다(한 색만 세는 음성 검사는 그 색이 안 쓰이게
되면 조용히 아무것도 안 본다).

| 심은 것 | 결과 |
|---|---|
| `\| grep -q X` · `-aq` · `-aqE` · `--quiet` · `rg -q` | 다섯 다 잡고 줄 번호를 가리킨다 |
| `grep -q X file`(파이프 없음) · `\| tail -20` · `\| grep Y >/dev/null` · `\| grep -v Y >/dev/null` | 넷 다 안 잡는다 |

대조군의 셋째·넷째가 GA-M0이 넣은 처방 모양이다. 처방이 lint를 통과하는
것을 직접 보지 않으면 둘 중 하나가 틀렸을 수 있다.

`cd "$(dirname "$0")"`를 조심한다. `check.sh`의 사본을 `/tmp`에서 돌리면
그 줄이 작업 디렉터리를 옮겨 체인 파일을 전부 못 찾고, 증상이 lint의 거짓
양성과 똑같이 생긴다. 잘라낸 사본에서 그 줄을 빼고 돌린다.

## 범위 밖

`head`와 `grep -m N`도 같은 병을 만들지만 이 저장소에 쓰인 자리가 없어
lint 범위에 안 넣었다. 없는 것을 막는 검사는 거짓 양성만 만든다.
`tail`은 애초에 대상이 아니다 — 입력을 끝까지 읽으므로 앞단을 죽이지 않는다.

`pipefail`을 끄는 것도 안 한다. 끄면 이 병이 사라지는 대신 파이프라인
앞단의 진짜 실패가 전부 조용해진다.
