# Render Cost (RC)

`HANDOFF.md`의 이월 숙제가 "첫 프레임 비용의 출처가 셀 배경 칠하기인지
`fill`의 102만 번 volatile 쓰기인지 안 갈렸다"고 오래 적어 두고 있었다.
**RC-M0이 2026-08-30에 그것을 쟀고 같은 날 끝났다.** 재기만 하는
milestone이라 **저장소의 코드는 한 줄도 안 바뀌었다.**

- design: `docs/superpowers/specs/2026-08-30-tars-render-cost-design.md`
- plan: `docs/superpowers/plans/2026-08-30-tars-render-cost-rc-m0.md`

## 답 — `fill`이다

화면이 찬 프레임 18개(부팅 3회)의 중앙값이다.

| 구간 | 중앙값 | 픽셀 | 최소에서 ns/px |
|---|---|---|---|
| `fill` | **18.0ms** | 1,024,000 | 8.27 |
| `glyph` | 1.5ms | 11,044 | 108.10 |
| `bg` | 0.9ms | 116,608 | 4.84 |
| `present` | 0.8ms | — | — |

**실제 프레임 21.3밀리초 중 `fill`이 84.7%, 셀 배경이 4.2%다.** 첫 프레임도
같다 — 셀이 하나뿐이라 `bg`와 `glyph`가 거의 0인데 `fill`이 20~24밀리초다.

**이 값들은 arm64 위 TCG 에뮬레이션의 것이다.** 절대값을 실제 하드웨어로
옮기지 않는다. 이 측정이 주는 것은 **구간 사이의 비율**이다.

## 재사용할 사실 셋

**1. 프레임버퍼 쓰기는 픽셀 수에 정비례한다.** 91,520픽셀과 1,024,000픽셀이
8.11 대 8.27 ns/px다. **4MB 버퍼를 통째로 훑어도 366KB만 훑을 때와 픽셀당
비용이 같다.** 착수 전에 걱정한 write-combining 불이익은 안 일어난다.

**2. `cells()`는 격자 전체를 안 준다.** `vt.zig:504`의
`if (cp == 0 and bg == default_bg) continue;`가 글자도 없고 배경도 기본인 셀을
목록에서 뺀다. `ls` 뒤 화면의 셀이 **7,285개가 아니라 911개**다. **화면 전체를
전제로 픽셀 수를 세면 여덟 배가 틀린다.**

**3. 시리얼 한 줄이 0.6~8.8밀리초다.** 게스트 안에서 시간을 재는 구간에
`std.debug.print`가 하나라도 들어가면 **그 값은 코드가 아니라 시리얼 콘솔의
비용이다.** 그래서 프로브가 `drm.zig`의 `kms: set crtc` print를 지웠다.

## 이 측정이 닫은 처방

**`fill`을 여백으로 좁히는 것은 한 픽셀도 못 아낀다.** 좁히려면 셀 배경
루프가 격자 전체를 칠해야 하고, 그러면 총 쓰기가 91,520 + 932,480 =
1,024,000으로 지금과 정확히 같다. **빈 곳의 바탕을 실제로 칠하는 것이
`fill`이고, `fill`은 여백 담당이 아니라 화면 지우개다.**

**`present`의 매 프레임 모드셋도 급하지 않다.** 착수 전에 "진짜 후보"로
의심했는데 실측은 4%였다.

**남은 길은 부분 갱신 하나뿐이다** — 안 바뀐 픽셀을 다시 안 쓰는 것.
`RenderState`가 dirty를 이미 준다. 다만 **게이트의 `style>`·`ink>` 덤프가 매
프레임 화면 전체를 전제로 하므로 게이트까지 함께 건드려야 한다.**

**그리고 그것을 하지 않기로 정했다.** 값을 본 사용자가 2026-08-30에 "당장
성능 문제는 없다, 추가 성능 개선은 나중에"로 정했다. **RC-M0은 "무엇이
비싼가"만 답했고 "사람이 느끼는가"는 안 쟀는데**, 21밀리초는 초당 47프레임이고
그 값도 TCG 위의 것이라 실제 하드웨어는 더 빠르다. **다시 집을 신호는 "사람이
느린 것을 느낀다"이지 "숫자가 크다"가 아니다.**

## 방법에서 배운 것

**프로브 사본은 손으로 옮겨 적지 않고 패치 스크립트로 만든다.** 원본을 읽어
정확한 치환을 적용하고 **anchor가 정확히 한 번 나오는지 단언**한다.
`main.zig`가 900줄이 넘어 손으로 만들면 조용히 어긋날 수 있는데, 이 방식은
원본이 바뀌면 시끄럽게 실패한다. `-v`로 원본 자리에 read-only 마운트하는 것은
[[project_copy_search_feedback]]의 CS-M0이 쓴 방법과 같다.

**검산이 통과해도 뜻이 맞는다는 보장은 없다.** 여백만 칠하는 반사실을 처음에는
화면 전체를 훑으며 `continue`로 건너뛰게 썼다 — 쓰기는 91,520번인데 루프는
1,024,000번 돈다. **`total`과 구간 합의 검산은 그대로 통과했다.** 잘못 잰 값도
합에는 정확히 들어가기 때문이다. **합이 맞는다는 것은 "못 잰 구간이 없다"만
말한다.**

**고정된 일의 비용은 최소값으로 비교한다.** 이 환경은 잡음이 커서 같은 구간의
폭이 3~18배다. 중앙값으로 보면 여백 칠하기가 `fill`보다 픽셀당 비싸 보이는데,
최소값으로 보면 8.11 대 8.27로 같다. **간섭이 가장 적었던 회차가 순수 비용에
가장 가깝다.** 게이트 시간의 잡음을 다루는
[[project_gate_latency]]와 같은 문제의 다른 얼굴이다.

## 협업 범위의 예외

`CLAUDE.md`는 구현 파일 편집을 사용자가 하도록 정하지만, **이번에는 사용자가
"측정이 목표이니 코드를 Claude가 직접 쓰라"고 지시했다**(2026-08-30). 프로브
판은 `/tmp`에 만들어 마운트하는 것이라 저장소에 안 들어가므로 그 검토 지점이
원래 성립하지 않는 자리이기도 하다. **저장소에 들어가는 파일이 생기면 원래
규칙으로 돌아간다.**
