# Zig 0.16 크래시 코스 — 코드를 읽기 위한 1주일 가이드

> 대상: `ghostty-vt`(`terminal/ghostty-src/`)와 우리 `terminal/src/*.zig`를
> 막힘 없이 읽는 것.
> 기준 버전: Zig 0.16.0 (`terminal/build.zig.zon`의 `minimum_zig_version`).
> 예제는 전부 이 저장소 안의 실제 코드에서 가져왔다 — 파일명:줄번호로 표기했다.

---

## 이 가이드의 전제

Zig 공식 문서는 0.16 변경사항을 아직 다 따라잡지 못했고, 인터넷에 있는
대부분의 Zig 예제는 0.11~0.14 시절 코드다. 그래서 "문법을 배웠는데 실제
코드가 안 읽히는" 상황이 생긴다. 원인은 문법이 아니라 세 가지다.

1. 0.16에서 표준 라이브러리가 크게 재편됐다 (`std.Io` 도입, `std.fs` 껍데기화,
   `ArrayList` unmanaged 전환, `main` 시그니처 변경).
2. Zig 코드는 소수의 관용구(idiom)를 반복해서 쓴다. 관용구를 모르면 문법을
   알아도 의도가 안 읽힌다.
3. C interop 코드는 Zig 문법이 아니라 C ABI 지식을 요구한다.

그래서 이 가이드는 문법 → 관용구 → 0.16 차이 → C interop 순으로 간다.
Day 6이 "인터넷 예제가 왜 컴파일 안 되는지" 답이고, Day 7이 우리 프로젝트가
실제로 하는 일이다.

## 하루 구성

각 Day는 이렇게 되어 있다.

- 개념: 왜 이렇게 생겼는지
- 실제 코드: 저장소 안의 인용
- 관용구: 그 날 배운 것 중 반복 등장하는 패턴
- 읽기 과제: 실제 파일 하나를 끝까지 읽기
- 확인 질문: 답을 스스로 말해보고 아래 답과 대조

하루 2~3시간을 상정했다. 코드를 직접 편집기에서 열어두고 읽는 것이 핵심이다.

# Day 1 — 파일, 선언, 값의 모양

## 1.1 파일이 곧 struct다

Zig에는 `class`도 `namespace` 키워드도 없다. 파일 하나가 이름 없는 struct
하나이고, `@import`는 그 struct 값을 돌려준다.

```zig
// terminal/src/vt.zig:1-2
const std = @import("std");
const ghostty_vt = @import("ghostty-vt");
```

`std`는 표준 라이브러리 struct, `ghostty-vt`는 `build.zig`에서 이름 붙여 준
모듈이다. 모듈 이름은 `build.zig`에서 정해진다.

```zig
// terminal/build.zig:29
exe_mod.addImport("ghostty-vt", ghostty_dep.module("ghostty-vt"));
```

즉 `@import("ghostty-vt")`가 되는 이유는 파일 시스템이 아니라 빌드 스크립트에
있다. 코드에서 낯선 `@import` 이름이 나오면 항상 `build.zig`를 먼저 본다.

파일 자체를 타입으로 쓰고 싶으면 `@This()`로 자기 자신을 잡는다. 이게
ghostty 코드에서 가장 자주 보이는 첫 줄이다.

```zig
// terminal/ghostty-src/src/terminal/Terminal.zig:1-4
//! The primary terminal emulation structure. ...
const Terminal = @This();
```

이 선언 뒤에 나오는 최상위 필드들이 그대로 `Terminal` struct의 필드가 된다.

```zig
// Terminal.zig:47-60 (발췌)
screens: ScreenSet,
status_display: ansi.StatusDisplay = .main,
tabstops: Tabstops,
rows: size.CellCountInt,
cols: size.CellCountInt,
```

읽는 법: 파일명이 대문자로 시작하면(`Terminal.zig`, `Parser.zig`,
`PageList.zig`) "이 파일 = 타입 하나"라는 뜻이다. 소문자 파일명
(`page.zig`, `sgr.zig`, `color.zig`)이면 "여러 타입/함수를 담은 네임스페이스"다.
이건 Zig 표준 라이브러리와 ghostty가 공유하는 관례이고, 디렉터리를 훑을 때
파일명만 보고 성격을 판단할 수 있게 해준다.

## 1.2 주석 세 종류

```zig
//! 파일 전체에 대한 문서 (파일 최상단에만 올 수 있다)
/// 바로 아래 선언에 대한 문서
//  일반 주석
```

`//!`가 파일 최상단에 있으면 그 파일의 역할 요약이다. 새 파일을 열면 여기부터
읽는다. `lib_vt.zig:1-9`가 좋은 예로, "이건 공개 API이고 안정성 보장은 없다"고
먼저 말해준다.

## 1.3 const와 var, 그리고 undefined

- `const`는 재대입 불가. 기본값으로 쓴다.
- `var`는 재대입 가능. 필요할 때만.
- `undefined`는 "값을 아직 안 정했다"는 명시적 표시다. 읽으면 UB다.

```zig
// terminal/src/pty.zig:24-25
var master_fd: c_int = undefined;
const pid = c.forkpty(&master_fd, null, null, null);
```

C 함수가 out-parameter로 채워줄 변수는 `undefined`로 시작한다. 이건 게으름이
아니라 "여기는 C가 채운다"는 신호다. Debug 빌드에서 Zig는 `undefined` 메모리를
`0xAA`로 채워서 실수로 읽으면 티가 나게 한다.

## 1.4 정수 타입은 비트 폭을 그대로 쓴다

Zig는 `u1`부터 `u65535`까지 임의 폭 정수를 지원한다. 이걸 장식이 아니라
설계 도구로 쓴다.

```zig
// page.zig 발췌
pub const ContentTag = enum(u2) { codepoint = 0, ... };
codepoint: packed struct(u24) { data: u21, _pad: u3 = 0 },
```

- `u21`: 유니코드 코드포인트 최대값이 U+10FFFF라 21비트면 충분하다.
- `u2`: 태그가 4종류라 2비트.
- `u24`: 세 필드가 공유하는 union의 크기를 정확히 맞추기 위함.

C 상호 운용용 타입은 따로 있다: `c_int`, `c_uint`, `c_long`, `c_ulong`,
`usize`, `isize`. `drm.zig`가 `fd: c_int`를 쓰는 이유는 리눅스 fd가 C의 `int`라서다.

시프트 연산에서 자주 걸린다.

```zig
// terminal/src/drm.zig:224
if (enc.possible_crtcs & (@as(u32, 1) << @as(u5, @intCast(i))) != 0) return crtc_id;
```

`u32`를 시프트할 때 시프트 양의 타입은 `u5`여야 한다 (2^5 = 32). Zig가
"시프트 양이 폭을 넘을 수 없음"을 타입으로 강제하기 때문이다. 이 `u5`가
갑자기 튀어나오면 당황하지 말고 "아, 시프트 대상이 u32구나"로 읽으면 된다.

## 1.5 배열, 슬라이스, 포인터 — 다섯 가지를 구분한다

이게 Zig 코드 읽기의 첫 번째 관문이다.

| 표기 | 의미 | 길이 정보 |
|---|---|---|
| `[N]T` | 길이 N 배열 (값) | 컴파일 타임 |
| `[]T` | 슬라이스 = 포인터 + 길이 | 런타임 |
| `*T` | 단일 항목 포인터 | 없음(항상 1개) |
| `[*]T` | 여러 항목 포인터 (C의 `T*`) | 없음 |
| `[*c]T` | C 포인터 (null 허용 + 위 둘 겸용) | 없음 |

여기에 sentinel(끝 표시)이 붙는다.

| 표기 | 의미 |
|---|---|
| `[:0]const u8` | 0으로 끝나는 슬라이스 (길이도 있음) |
| `[*:0]const u8` | 0으로 끝나는 포인터 = C의 `const char*` |
| `[*:null]const ?[*:0]const u8` | null로 끝나는 문자열 포인터 배열 = C의 `char* argv[]` |

실제 코드에서 어떻게 쓰이는지 보자.

```zig
// terminal/src/pty.zig:12
extern "c" fn execv(path: [*:0]const u8, argv: [*:null]const ?[*:0]const u8) c_int;

// terminal/src/pty.zig:29-35
const argv = [_:null]?[*:0]const u8{
    "fish",
    "--no-config",
    "-c",
    command.ptr,
};
_ = execv("/usr/bin/fish", &argv);
```

읽는 법:
- `[_:null]?[*:0]const u8{...}` — `_`는 길이를 컴파일러가 세라는 뜻, `:null`은
  마지막에 null 항목을 자동으로 붙이라는 뜻.
- `?[*:0]const u8` — nullable한 C 문자열 포인터. `argv` 배열의 마지막이 null이라
  optional이어야 한다.
- `command.ptr` — `[:0]const u8` 슬라이스에서 포인터만 꺼낸다. sentinel 정보는
  타입에 남아 있어서 `[*:0]const u8`가 된다.
- `&argv` — 배열의 주소를 넘기면 `*[N:null]...`이 되고, 이게 `[*:null]...`로
  자동 강제 변환(coercion)된다.

문자열 리터럴 `"fish"`의 타입은 `*const [4:0]u8`이다. 배열 포인터. 그래서
`[*:0]const u8`로도, `[]const u8`로도 자동 변환된다.

슬라이싱은 `buf[a..b]`이고, 이건 새 슬라이스를 만든다(복사 아님).

```zig
// terminal/src/pty.zig:52
return buf[0..total];
```

## 1.6 함수와 반환

```zig
// terminal/src/font.zig:65
pub fn find(cache: GlyphCache, codepoint: u32) ?Glyph {
```

- `pub`가 없으면 파일 밖에서 안 보인다.
- 파라미터는 기본이 값 전달이고 불변이다. 함수 안에서 `cache = ...` 못 한다.
  바꿔야 하면 `*T`를 받는다.
- 큰 struct를 값으로 받아도 컴파일러가 알아서 포인터로 넘길 수 있다
  (파라미터가 불변이라 가능한 최적화다).

self 메서드는 첫 인자 이름을 `self`로 쓰는 관례일 뿐, 언어 기능이 아니다.

```zig
// terminal/src/drm.zig:128
pub fn setPixel(self: Framebuffer, x: u32, y: u32, color: u32) void {
// terminal/ghostty-src/src/terminal/Terminal.zig:349
pub fn deinit(self: *Terminal, alloc: Allocator) void {
```

값을 안 바꾸면 `self: T`, 바꾸면 `self: *T`. 이 구분만 봐도 그 함수가 상태를
건드리는지 즉시 알 수 있다 — 읽을 때 아주 유용한 신호다.

## 1.7 반복문의 두 형태

```zig
// for: 슬라이스/배열 순회, 인덱스는 0.. 을 추가로 넘긴다
// terminal/src/font.zig:34
for (codepoints, 0..) |codepoint, i| {

// terminal/src/drm.zig:223
for (crtc_ids, 0..) |crtc_id, i| {

// while + continue expression: C의 for(;;i++)에 해당
// terminal/src/drm.zig:136-138
var row: u32 = 0;
while (row < self.height) : (row += 1) {
```

`for (a, b) |x, y|`처럼 여러 슬라이스를 동시에 순회할 수 있고, 이때 길이가
다르면 런타임 패닉이다. `0..`은 무한 범위처럼 보이지만 다른 인자의 길이에
맞춰진다.

`for (0..state.rows) |y|`처럼 숫자 범위만 도는 것도 된다 (`vt.zig:36`).

## 확인 질문 (Day 1)

Q. `[]const u8`과 `[*:0]const u8`은 어떤 상황에서 각각 필요한가?
A. Zig 내부에서 문자열을 다룰 땐 길이가 있는 `[]const u8`이 안전하고 빠르다.
C 함수에 넘길 땐 C가 길이를 모르고 0을 찾으므로 `[*:0]const u8`이어야 한다.
`pty.zig`가 `command: [:0]const u8`을 받는 이유가 이것 — 둘 다 만족시키려고
"길이도 있고 0으로도 끝나는" 타입을 골랐다.

Q. `var master_fd: c_int = undefined;`가 안전한 이유는?
A. 바로 다음 줄에서 `forkpty(&master_fd, ...)`가 값을 채우고, 그 전에 읽지
않기 때문이다. Zig는 이 안전성을 검사해주지 않는다 — `undefined`는 개발자가
책임지겠다는 선언이다.

# Day 2 — 에러, optional, switch

## 2.1 에러는 값이다

Zig에는 예외가 없다. 에러는 반환 타입에 섞인다.

```zig
// terminal/src/drm.zig:112-115
fn drmIoctl(fd: c_int, request: u32, arg: *anyopaque) !void {
    const rc = c.ioctl(fd, @as(c_ulong, request), arg);
    if (rc < 0) return error.IoctlFailed;
}
```

- `!void` = "에러 아니면 void". 앞에 에러 집합을 안 쓰면 컴파일러가 추론한다.
- `error.IoctlFailed`는 그 자리에서 새 에러 태그를 만든다. 별도 선언이 없어도
  된다 — 같은 이름은 전역적으로 같은 에러다.

명시적 에러 집합도 흔하다.

```zig
// terminal/ghostty-src/src/terminal/c/terminal.zig:59
pub const Error = error{OutOfMemory};
```

에러 집합끼리는 `||`로 합친다. 표준 라이브러리에서 자주 본다.

```zig
// std/process.zig
pub const CurrentPathError = error{
    NameTooLong,
    CurrentDirUnlinked,
} || Io.Cancelable || Io.UnexpectedError;
```

## 2.2 try / catch / errdefer

`try f()`는 `f() catch |err| return err`의 축약이다.

```zig
// terminal/src/drm.zig:233-241
const resources = try getResources(allocator, fd);
const found = try findConnectedConnector(allocator, fd, resources.connector_ids);
const encoder_id = if (found.connector.encoder_id != 0)
    found.connector.encoder_id
else if (found.encoders.len > 0)
    found.encoders[0]
else
    return error.NoEncoders;
```

`if`가 식(expression)이라 `const x = if (...) a else b;`가 된다. `else` 가지에서
`return`으로 빠져나가는 것도 자연스럽다 (`noreturn` 타입이 어떤 타입에도 맞기
때문이다).

`catch`는 기본값을 주거나 처리할 때 쓴다.

```zig
// c/terminal.zig:70-71
const ptr = alloc.create(std.Io.Threaded) catch
    return error.OutOfMemory;
```

`errdefer`는 "에러로 함수를 빠져나갈 때만" 실행되는 정리다. 부분적으로 초기화된
상태를 되돌릴 때 쓴다.

```zig
// Terminal.zig:314-317
var screen_set: ScreenSet = try .init(io_impl, alloc, .{ ... });
errdefer screen_set.deinit(alloc);
```

읽는 법: `try X` 다음 줄에 `errdefer X.deinit()`이 오는 쌍은 Zig에서 거의
반사적인 패턴이다. 이 두 줄이 붙어 있지 않으면 누수를 의심할 수 있다.

## 2.3 defer

`defer`는 스코프를 벗어날 때(성공이든 실패든) 실행된다. 등록 역순으로 실행된다.

```zig
// terminal/src/vt.zig:20-32
var t: ghostty_vt.Terminal = try .init(io, alloc, .{ .cols = cols, .rows = rows });
defer t.deinit(alloc);

var stream = t.vtStream();
defer stream.deinit();

var state: ghostty_vt.RenderState = .empty;
defer state.deinit(alloc);

var out: std.ArrayList(CellGlyph) = .empty;
defer out.deinit(alloc);
```

핵심 습관: 자원을 얻은 바로 다음 줄에 해제를 쓴다. 함수가 길어져도 짝이
눈에 보인다. C의 `goto cleanup` 사다리가 사라지는 지점이다.

주의: `vt.zig:31-50`에서 `out`은 `defer out.deinit(alloc)`을 걸어두고도
마지막에 `out.toOwnedSlice(alloc)`으로 소유권을 넘긴다. `toOwnedSlice`가
리스트를 빈 상태로 만들기 때문에 뒤이어 실행되는 `deinit`이 아무것도 해제하지
않는다. 이건 의도된 관용구다.

## 2.4 optional

`?T`는 "T 아니면 null". 포인터에 null이 섞이지 않게 타입으로 분리한 것이다.

```zig
// terminal/src/main.zig:20
const bitmap = glyph.bitmap orelse return;
```

`orelse`는 null일 때의 대체값 또는 탈출이다.

```zig
// terminal/src/main.zig:66
if (font.find(cache, cell.codepoint)) |glyph| {
```

`if (opt) |v|`는 "null이 아니면 v로 언랩". 이 형태를 알아보는 게 중요하다 —
`if` 뒤의 `|...|`는 언제나 언랩(unwrap)이다.

에러 언랩도 같은 모양이다.

```zig
if (mayFail()) |value| {
    // 성공
} else |err| {
    // 실패, err로 접근
}
```

`|value|`는 성공값, `else |err|`는 에러값. optional엔 `else |err|`가 없다는
점으로 둘을 구분한다.

null 반환은 "실패"가 아니라 "없음"을 뜻할 때 쓴다.

```zig
// terminal/src/font.zig:65-70
pub fn find(cache: GlyphCache, codepoint: u32) ?Glyph {
    for (cache.glyphs) |glyph| {
        if (glyph.codepoint == codepoint) return glyph;
    }
    return null;
}
```

폰트에 글자가 없는 건 에러가 아니라 "그릴 게 없음"이다. 이 구분(에러 vs
optional)이 API 설계의 의도를 드러낸다.

## 2.5 switch는 완전해야 한다

```zig
// Terminal.zig:397-400 (발췌)
self.modes.set(.cursor_blinking, switch (value) {
    .default => self.cursor.default_blink orelse true,
    .steady_block, .steady_bar, .steady_underline => false,
    ...
});
```

- enum을 switch하면 모든 항목을 다루거나 `else`를 써야 한다. 새 enum 항목을
  추가하면 컴파일 에러로 누락된 곳을 전부 잡아준다.
- `.default`처럼 타입 이름 없이 점만 찍는 건 enum literal이다. 문맥에서
  타입이 결정되면 이름을 생략한다. Zig 코드가 짧아 보이는 큰 이유 중 하나다.
- `a, b, c => expr`로 여러 값을 묶고, `0...9 => expr`로 범위를 쓴다.
- switch도 식이다.

## 2.6 labeled block

블록에서 값을 꺼내야 할 때 라벨을 쓴다.

```zig
// terminal/ghostty-src/src/lib_vt.zig:376-414 (요약)
pub const std_options: std.Options = opts: {
    var options: std.Options = .{};
    if (builtin.target.cpu.arch.isWasm()) {
        options.log_level = switch (builtin.mode) { ... };
        options.logFn = @import("os/wasm/log.zig").log;
    }
    ...
    break :opts options;
};
```

`이름: { ... break :이름 값; }`은 "여러 줄 계산해서 값 하나 만들기"다. 이게
없으면 초기화 함수를 따로 만들어야 한다. 위 코드는 comptime에 실행되는
상수 초기화라 특히 자주 이 형태를 쓴다.

## 확인 질문 (Day 2)

Q. `defer`와 `errdefer`를 함께 쓸 때 어떤 조합이 맞는가?
A. 함수가 자원을 소유한 채 끝나면 `defer`, 함수가 성공 시 자원을 호출자에게
넘겨준다면 `errdefer`. `Terminal.init`이 `errdefer screen_set.deinit(alloc)`을
쓴 이유는 성공 시 `screen_set`이 반환값 안에 살아남기 때문이다.

Q. `catch unreachable`은 무슨 뜻인가?
A. "여기서 에러가 절대 안 난다고 내가 보증한다"는 뜻. Debug/ReleaseSafe에서
실제로 에러가 나면 패닉하고, ReleaseFast에서는 UB다. 잘못 쓰면 위험하니
읽을 때 근거가 명시돼 있는지 확인한다.

# Day 3 — 메모리, allocator, 그리고 decl literal

## 3.1 할당자는 인자로 흘러다닌다

Zig에는 전역 힙이 없다. 메모리를 쓰는 함수는 `std.mem.Allocator`를 받는다.

```zig
// terminal/src/vt.zig:13-19
pub fn parseToCells(
    io: std.Io,
    alloc: std.mem.Allocator,
    bytes: []const u8,
    cols: u16,
    rows: u16,
) ![]CellGlyph {
```

이게 Zig 코드를 읽을 때 가장 유용한 신호다.

- 시그니처에 `Allocator`가 없다 → 이 함수는 힙을 안 쓴다. 정리할 것도 없다.
- 있다 → 어딘가에서 `alloc.alloc` / `alloc.create`가 일어나고, 짝이 되는
  해제 책임이 어딘가에 있다.

우리 `pty.readAll`이 좋은 대비다.

```zig
// terminal/src/pty.zig:45
pub fn readAll(fd: c_int, buf: []u8) []const u8 {
```

호출자가 버퍼를 주고(`main.zig:53`의 `var pty_buf: [4096]u8 = undefined;`),
함수는 할당하지 않는다. 커널/임베디드 코드에서 선호되는 형태다.

Allocator 종류는 상황에 따라 고른다.

- `std.heap.page_allocator` — mmap 직행. 큰 덩어리, 해제 신경 안 쓰는 단명
  프로그램용. `main.zig:34`가 이걸 쓴다.
- `std.heap.ArenaAllocator` — 통째로 한 번에 해제. 파싱/요청 단위 작업에 좋다.
- `std.heap.DebugAllocator` (구 GeneralPurposeAllocator) — 누수/이중 해제 검출.
- `std.testing.allocator` — 테스트에서 누수가 있으면 테스트를 실패시킨다.

0.16에서는 `std.process.Init`이 `gpa`와 `arena`를 이미 만들어서 `main`에
넘겨준다 (Day 6에서 자세히).

## 3.2 unmanaged가 기본이다

0.16의 `std.ArrayList`는 allocator를 필드로 들고 있지 않다. 매 메서드에
allocator를 넘긴다. (예전 방식은 `std.array_list.Managed`로 남아 있지만
deprecated다 — 인터넷 예제가 여기서 깨진다.)

```zig
// terminal/src/vt.zig:31-50
var out: std.ArrayList(CellGlyph) = .empty;
defer out.deinit(alloc);
...
try out.append(alloc, .{ ... });
...
return out.toOwnedSlice(alloc);
```

왜 이렇게 바꿨나: 컨테이너가 allocator 포인터를 안 들고 있으면 struct가
작아지고(16바이트 대신 24바이트를 아끼는 수준이 아니라, 수천 개를 중첩할 때
차이가 커진다), 컨테이너를 다른 allocator로 옮기기도 쉬워진다. ghostty처럼
셀 하나하나가 메모리인 프로그램에는 중요한 차이다.

`render.zig:125`가 실제 사용례다.

```zig
pending_styles: std.ArrayList(StyleRun) = .empty,
```

struct 필드 기본값으로 `.empty`를 그냥 쓸 수 있다 — allocator가 필요 없으니까.

## 3.3 decl literal — 점 하나로 시작하는 초기화

Zig 0.14부터 들어온 문법이고, 0.16 코드에서는 거의 표준이다. 타입이 이미
정해진 자리에서는 타입 이름을 생략하고 그 타입의 선언(declaration)에 바로
접근할 수 있다.

```zig
// terminal/src/vt.zig:20
var t: ghostty_vt.Terminal = try .init(io, alloc, .{ .cols = cols, .rows = rows });
```

`.init`은 `ghostty_vt.Terminal.init`이다. 왼쪽에 타입을 썼으니 오른쪽에서
반복하지 않는다. `try`가 `.init` 앞에 오는 배치가 처음엔 낯설지만 익숙해진다.

```zig
// terminal/src/vt.zig:27
var state: ghostty_vt.RenderState = .empty;
// Terminal.zig:318-341 (발췌)
var result: Terminal = .{
    .cols = cols,
    .rows = rows,
    .tabstops = try .init(alloc, cols, TABSTOP_INTERVAL),
    .pwd = .empty,
    .title = .empty,
    .modes = .{ .values = opts.default_modes, .default = opts.default_modes },
};
```

`.tabstops = try .init(...)`처럼 필드 타입에서 추론되는 것까지 된다. 이게
0.16 코드가 이전 버전과 시각적으로 가장 다르게 보이는 지점이다.

읽는 법: 점으로 시작하는 것이 나오면 왼쪽(선언된 타입, 함수 파라미터 타입,
반환 타입)에서 타입을 찾는다. 세 종류가 있다.

| 형태 | 이름 | 예 |
|---|---|---|
| `.foo` (enum 자리) | enum literal | `.main`, `.narrow` |
| `.{ .a = 1 }` | anonymous struct literal | `.{ .cols = 80 }` |
| `.init(...)`, `.empty` | decl literal | `try .init(alloc)` |

## 3.4 deinit의 관용구

```zig
// Terminal.zig:349-356
pub fn deinit(self: *Terminal, alloc: Allocator) void {
    self.tabstops.deinit(alloc);
    self.screens.deinit(alloc);
    self.pwd.deinit(alloc);
    self.title.deinit(alloc);
    self.glyph_glossary.deinit(alloc);
    self.* = undefined;
}
```

마지막 `self.* = undefined;`가 관용구다. 해제된 struct를 다시 쓰면 Debug
빌드에서 `0xAA` 패턴을 만나 바로 터지게 만든다. use-after-free를 조기에
드러내는 장치다.

# Day 4 — struct, enum, union, 그리고 메모리 레이아웃

## 4.1 struct 세 종류

| 종류 | 레이아웃 | 용도 |
|---|---|---|
| `struct` | 컴파일러 자유 (필드 재배치/패딩 가능) | Zig 내부용 |
| `extern struct` | C ABI와 동일 | C 구조체 대응 |
| `packed struct(u64)` | 비트 단위로 꽉 채움, backing 정수 지정 | 비트필드/직렬화 |

`drm.zig`가 `extern struct`를 쓰는 이유는 커널 ioctl이 정확한 바이트 배치를
요구하기 때문이다.

```zig
// terminal/src/drm.zig:69-77
const DrmModeCreateDumb = extern struct {
    height: u32 = 0,
    width: u32 = 0,
    bpp: u32 = 0,
    flags: u32 = 0,
    handle: u32 = 0,
    pitch: u32 = 0,
    size: u64 = 0,
};
```

여기서 `extern`을 빼면 컴파일러가 필드를 재배치해도 되고, 커널에 쓰레기가
전달된다. C 헤더의 구조체를 손으로 옮길 때는 반드시 `extern struct`다.

필드 기본값 `= 0`을 전부 달아둔 덕분에 호출부가 짧아진다.

```zig
// terminal/src/drm.zig:255
var map: DrmModeMapDumb = .{ .handle = dumb.handle };
```

나머지 필드는 기본값 0으로 채워진다. 커널에 넘기는 구조체는 미초기화
바이트가 있으면 안 되므로 이 습관이 중요하다.

## 4.2 packed struct — 비트 단위 설계

ghostty의 셀 하나는 정확히 64비트다.

```zig
// terminal/ghostty-src/src/terminal/page.zig:2049
pub const Cell = packed struct(u64) {
    content_tag: ContentTag = .codepoint,     // u2
    content: packed union {
        codepoint: packed struct(u24) { data: u21, _pad: u3 = 0 },
        color_palette: packed struct(u24) { data: u8, _pad: u16 = 0 },
        color_rgb: RGB,                        // u24
    } = .{ .codepoint = .{ .data = 0 } },
    style_id: StyleId = 0,                     // u16
    wide: Wide = .narrow,                      // u2
    protected: bool = false,                   // u1
    hyperlink: bool = false,                   // u1
    semantic_content: SemanticContent = .output, // u2
    _padding: u16 = 0,
```

읽는 법:
- `packed struct(u64)`의 괄호 안이 backing 정수다. 필드 폭 합이 정확히 64가
  아니면 컴파일 에러다 — 그래서 `_pad`, `_padding` 필드가 명시적으로 있다.
- `packed union`은 모든 변형이 같은 비트를 공유한다. 어떤 변형이 유효한지는
  `content_tag`가 알려준다 — 즉 손으로 만든 태그드 유니온이다. 왜 언어의
  `union(enum)`을 안 썼나? 그건 태그 저장에 추가 바이트를 쓰고 packed에 못
  넣기 때문이다. 64비트에 맞추려는 설계 결정이다.
- `bool`은 packed 안에서 1비트다.

backing 정수로 왕복하는 관용구:

```zig
// page.zig:2147 부근
pub const Backing = @typeInfo(Cell).@"struct".backing_integer.?;
pub const C = u64;
pub fn cval(self: Cell) C { return @bitCast(self); }
```

`@bitCast`는 비트를 그대로 재해석한다(크기가 같아야 함). C API로 셀을 내보낼
때 구조체 대신 `u64` 하나를 넘기는 트릭이 여기서 나온다.

주석도 읽어둘 가치가 있다.

```zig
// page.zig, Cell.init
// We have to use this bitCast here to ensure that our memory is
// zeroed. Otherwise, the content below will leave some uninitialized
// memory in the packed union. Valgrind verifies this.
var cell: Cell = @bitCast(@as(u64, 0));
```

packed union은 가장 짧은 변형을 쓰면 나머지 비트가 미초기화로 남는다. 그래서
0으로 통째로 만든 뒤 필드를 채운다. 이런 주석이 Zig 코드의 진짜 학습 자료다.

## 4.3 enum

```zig
pub const ContentTag = enum(u2) { codepoint = 0, codepoint_grapheme = 1, ... };
pub const Wide = enum(u2) { narrow = 0, wide = 1, spacer_tail = 2, spacer_head = 3 };
```

`enum(u2)`로 표현 타입을 고정한다. `@intFromEnum` / `@enumFromInt`로 정수와
왕복한다. 후자는 유효하지 않은 값이면 Safe 모드에서 패닉이다.

태그 없는 상태 머신 enum도 흔하다.

```zig
// Parser.zig:15-30
pub const State = enum {
    ground, escape, escape_intermediate,
    csi_entry, csi_intermediate, csi_param, csi_ignore,
    dcs_entry, dcs_param, dcs_intermediate, dcs_passthrough, dcs_ignore,
    osc_string, sos_pm_apc_string,
};
```

이게 vt100.net의 DEC ANSI 파서 상태 다이어그램 그대로다. 터미널 코드를 읽을
때 이 enum이 지도 역할을 한다.

## 4.4 tagged union — Zig 코드에서 가장 중요한 자료구조

```zig
// Parser.zig:49-77
pub const Action = union(enum) {
    pub const Tag = std.meta.FieldEnum(Action);

    print: u21,
    execute: u8,
    csi_dispatch: CSI,
    esc_dispatch: ESC,
    osc_dispatch: osc.Command,
    dcs_hook: DCS,
    dcs_put: u8,
    dcs_unhook: void,
    apc_start: void,
    apc_put: u8,
    apc_end: void,
};
```

- `union(enum)`은 태그를 컴파일러가 자동 생성하는 태그드 유니온이다.
- `dcs_unhook: void`처럼 payload 없는 변형도 있다. 이건 "그냥 이벤트"라는 뜻.

태그 enum을 직접 지정하는 형태도 있다.

```zig
// stream.zig:35-40
pub const Action = union(Key) {
    print: Print,
    print_slice: PrintSlice,
    print_repeat: usize,
    bell,
    backspace,
    ...
};
```

`bell,`처럼 타입 없이 쓰면 `void` payload다. `union(Key)`는 태그 enum을
따로 정의해서 재사용한다는 뜻이다.

소비하는 쪽은 switch + capture다.

```zig
// stream_terminal.zig 발췌 형태
switch (action) {
    .print => |cp| ...,
    .csi_dispatch => |csi_cmd| ...,
    .osc_dispatch => |cmd| switch (cmd) {
        .set => |set| switch (set.key) {
            .palette => |i| ...,
            .dynamic => |dynamic| switch (dynamic) { ... },
        },
        .reset => |target| ...,
    },
}
```

`|x|`가 payload를 꺼내고, 중첩 union은 중첩 switch로 내려간다. `|*x|`로
포인터 캡처를 하면 그 자리에서 수정할 수 있다 (`.kitty => |*kitty_cmd|`).

이 패턴을 눈에 익히면 `stream_terminal.zig` 같은 1000줄짜리 dispatch 파일도
"union 하나를 펼친 것"으로 읽힌다.

## 4.5 MultiArrayList — struct of arrays

우리 `vt.zig`가 바로 쓰는 자료구조라 짚고 간다.

```zig
// render.zig:97, 226
row_data: std.MultiArrayList(Row),
cells: std.MultiArrayList(Cell),
```

`MultiArrayList(T)`는 `[]T` 대신 각 필드를 별도 배열로 저장한다(SoA). 한 필드만
순회할 때 캐시 효율이 좋고, 필드별 정렬로 패딩이 준다.

접근 방법이 일반 배열과 달라서 처음엔 낯설다.

```zig
// terminal/src/vt.zig:34-41
const row_data = state.row_data.slice();   // Slice 핸들 얻기
const row_cells = row_data.items(.cells);  // .cells 필드만 모은 배열
for (0..state.rows) |y| {
    const cells_slice = row_cells[y].slice();
    const raws = cells_slice.items(.raw);   // .raw 필드 배열
    for (0..state.cols) |x| {
        const cp = raws[x].codepoint();
```

읽는 법: `.slice()` → `.items(.필드명)` 두 단계가 항상 따라온다.
`.items(.raw)`의 `.raw`는 enum literal로 표현된 필드 이름이다 (Day 5의
`std.meta.FieldEnum`과 같은 원리).

1. `page.zig`의 `Cell`(2049줄부터)과 `Row`(1940줄부터)를 읽고, 각 필드가

2. `Parser.zig`의 `Action`(49줄부터)을 읽고, 터미널 파서가 상위 코드에

## 확인 질문 (Day 4)

Q. `Cell`이 `union(enum)` 대신 `content_tag` + `packed union` 조합을 쓴 이유는?
A. `union(enum)`은 태그를 별도 필드로 두고 정렬 요구도 생겨서 64비트에 못 들어
간다. 셀은 화면 하나에 수만 개가 있으므로 크기가 성능/메모리에 직결된다.
안전성(태그 자동 관리)을 포기하고 크기를 얻은 트레이드오프다.

Q. `extern struct`와 `packed struct`는 언제 각각 쓰는가?
A. C 구조체와 바이트 배치를 맞춰야 하면 `extern struct` (필드는 자연 정렬,
패딩 존재). 비트 단위로 꽉 채우거나 정수로 왕복해야 하면 `packed struct`.
`drm.zig`의 UAPI 구조체는 전자, `page.zig`의 Cell은 후자.

# Day 5 — comptime과 제네릭

## 5.1 comptime은 별도 언어가 아니다

Zig에는 템플릿 문법이 없다. 컴파일 타임에 실행되는 보통의 Zig 코드가 있을
뿐이다. 타입도 값이다.

가장 단순한 형태: 타입을 받아 타입을 돌려주는 함수 = 제네릭.

```zig
// terminal/ghostty-src/src/terminal/stream.zig:465-470
pub fn Stream(comptime H: type) type {
    return struct {
        const Self = @This();

        pub const Handler = H;
```

읽는 법:
- `Stream(SomeHandler)`를 쓰면 그 순간 새 struct 타입이 만들어진다.
- 안에서 자기 타입을 참조하려면 `const Self = @This();`를 선언한다. 이름 없는
  struct라 다른 방법이 없다. ghostty에서 `Self`가 나오면 십중팔구 제네릭이다.
- `pub const Handler = H;`처럼 타입 파라미터를 다시 노출하면 호출자가
  `MyStream.Handler`로 꺼내 쓸 수 있다.

`Terminal`이 이걸 어떻게 소비하는지:

```zig
// Terminal.zig:30
const Stream = @import("stream_terminal.zig").Stream;
// Terminal.zig:373-378
pub fn vtStream(self: *Terminal) Stream {
    return Stream.init(.{
        .allocator = self.gpa(),
        .handler = self.vtHandler(),
    });
}
```

`stream_terminal.zig`가 이미 핸들러를 고정해서 `Stream`을 구체 타입으로
만들어 둔 것이다. 우리 `vt.zig:23`의 `var stream = t.vtStream();`이 여기로
이어진다.

## 5.2 comptime 분기로 코드를 지운다

```zig
// c/terminal.zig:53-57
const Impl = if (builtin.os.tag != .freestanding)
    *std.Io.Threaded
else
    void;
```

타입 자체를 조건부로 정한다. `void` 타입 필드는 크기가 0이라 struct에서
사라진다 — freestanding에서는 이 필드가 실제로 존재하지 않게 된다.

```zig
// c/terminal.zig:64-71
pub fn init(alloc: std.mem.Allocator) Error!Io {
    if (comptime builtin.os.tag == .freestanding) return .{ .impl = {} };
    const ptr = alloc.create(std.Io.Threaded) catch return error.OutOfMemory;
    ...
}
```

`if (comptime ...)`는 "이 조건은 컴파일 타임에 확정되고, 거짓 가지는 아예
분석/생성하지 말라"는 뜻이다. `{}`는 void 값이다.

`Terminal.zig`의 빌드 옵션 분기도 같은 원리다.

```zig
// Terminal.zig:286-294
kitty_image_storage_limit: usize = switch (build_options.artifact) {
    .ghostty => 320 * 1000 * 1000,
    .lib => 10 * 1000 * 1000,
},
```

`build_options`는 `build.zig`가 주입하는 모듈이다. 즉 빌드 스크립트의 옵션이
소스에서 상수처럼 보인다. `@import("terminal_options")` 형태(Terminal.zig:7)가
그것이고, 이런 import를 만나면 파일 시스템이 아니라 `build.zig`를 봐야 한다.

## 5.3 리플렉션 빌트인

컴파일 타임에 타입 정보를 들여다볼 수 있다.

```zig
// page.zig
pub const Backing = @typeInfo(Cell).@"struct".backing_integer.?;
// Parser.zig:50
pub const Tag = std.meta.FieldEnum(Action);
```

- `@typeInfo(T)`는 타입 정보를 태그드 유니온으로 준다. `.@"struct"`처럼
  따옴표를 쓰는 건 `struct`가 키워드라서다 (`@"..."`는 임의 식별자 표기).
- `std.meta.FieldEnum(T)`는 T의 필드 이름들로 enum을 만든다. 이게
  `MultiArrayList.items(.cells)`에서 `.cells`가 동작하는 원리다.

자주 쓰는 빌트인 요약:

| 빌트인 | 하는 일 |
|---|---|
| `@This()` | 현재 struct 타입 |
| `@typeInfo(T)` | 타입 메타정보 |
| `@sizeOf(T)`, `@alignOf(T)` | 크기/정렬 |
| `@intCast`, `@intFromEnum`, `@enumFromInt` | 정수/enum 변환 |
| `@bitCast` | 같은 크기 비트 재해석 |
| `@ptrCast`, `@alignCast` | 포인터 타입/정렬 변환 |
| `@intFromPtr`, `@ptrFromInt` | 포인터 ↔ 정수 |
| `@as(T, x)` | 명시적 타입 강제 |
| `@export`, `@extern` | 심볼 내보내기/가져오기 |

0.16에서는 `@intCast` 등이 결과 타입을 문맥에서 추론한다. 그래서
`@as(u32, @intCast(i))`처럼 두 개가 겹쳐 나오는 코드를 자주 본다
(`drm.zig:224`). 안쪽이 값 변환, 바깥쪽이 타입 확정이다.

## 5.4 comptime 블록과 @export

파일 최상단의 `comptime { ... }` 블록은 컴파일 시점에 무조건 실행된다.
ghostty는 여기서 C ABI 심볼을 내보낸다.

```zig
// lib_vt.zig:147-172 (발췌)
comptime {
    if (@import("root") == lib) {
        _ = @import("quirks_memset.zig");
        const c = terminal.c_api;
        @export(&c.key_event_new, .{ .name = "ghostty_key_event_new" });
        @export(&c.key_event_free, .{ .name = "ghostty_key_event_free" });
        ...
    }
}
```

읽는 법:
- `@import("root")`는 컴파일의 최상위 파일이다. `== lib`(자기 자신) 비교로
  "지금 이 파일이 루트인가?"를 판단한다. 즉 C 라이브러리로 빌드될 때만
  심볼을 내보내고, Zig 모듈로 import될 때는 안 내보낸다.
- `_ = @import("...")`는 "쓰지는 않지만 컴파일에 포함시켜라"다. 사이드 이펙트
  (여기서는 memset override export)를 위해 참조만 걸어두는 관용구다.

우리에게 이게 중요한 이유: 우리는 Zig 모듈 경로로 `ghostty-vt`를 쓰므로
(`build.zig:29`) 이 320줄짜리 `@export` 목록은 전부 컴파일에서 빠진다. C API로
쓸 때만 나타난다. 같은 소스가 두 얼굴을 갖는 방식이다.

## 5.5 inline

```zig
// stream.zig:584
pub inline fn nextSlice(self: *Self, input: []const u8) void {
```

`inline fn`은 강제 인라인이다. 핫 루프에서 분기 예측을 살리려고 쓴다.
`inline for` / `inline while`은 루프를 컴파일 타임에 펼친다 — 각 반복에서
타입이 달라져야 할 때 필수다.

## 읽기 과제 (Day 5)

`stream.zig`의 465~640줄. `Stream(comptime H: type) type` 안에서
`nextSlice` → `nextSliceUntracked` → `nextSliceCapped`로 내려가는 흐름을
읽는다. `if (comptime debug or !build_options.simd)`가 SIMD 경로를 통째로
지우는 방식(596~599줄)에 주목한다.

## 확인 질문 (Day 5)

Q. `const Self = @This();`가 제네릭 함수 안에서 필수인 이유는?
A. `fn Stream(comptime H: type) type`이 돌려주는 struct는 이름이 없다.
`Stream(H)`라고 자기를 부르면 무한 재귀가 되고, 다른 이름도 없다. `@This()`만이
"지금 이 struct"를 가리킬 수 있다.

Q. `if (comptime x)`와 그냥 `if (x)`의 차이는?
A. `comptime`을 붙이면 조건이 컴파일 타임에 평가되어야 하고, 선택되지 않은
가지는 의미 분석조차 되지 않는다. 그래서 특정 플랫폼에만 존재하는 API를
호출하는 코드를 다른 플랫폼에서 컴파일 에러 없이 배제할 수 있다.

# Day 6 — 0.16에서 달라진 것 (인터넷 예제가 안 되는 이유)

이 날이 실전에서 가장 자주 쓰인다. 오래된 예제를 만났을 때 어디를 의심할지
목록으로 정리한다. 아래 내용은 호스트에 설치된 Zig 0.16.0의 표준 라이브러리
소스(`/opt/homebrew/Cellar/zig/0.16.0_1/lib/zig/std`)와 대조해 확인했다.

## 6.1 std.Io — 가장 큰 변화

I/O가 "전역 기능"에서 "명시적으로 넘기는 인터페이스"가 됐다. allocator에
했던 일을 I/O에도 한 것이다.

```zig
// std/std.zig:19
pub const Io = @import("Io.zig");
```

`std.Io` 밑에 있는 것들:

```
std/Io/  Dir.zig  File.zig  Reader.zig  Writer.zig  Threaded.zig
         net.zig  Uring.zig  Kqueue.zig  fiber.zig  ...
```

그 결과 `std.fs`는 거의 비었다. 0.16의 `std/fs.zig`에 남은 공개 선언은
`path`, base64 인코더, 그리고 `max_path_bytes` 같은 상수뿐이고, 실제 정의는
전부 `std.Io.Dir` / `std.Io.File`로 옮겨갔다.

```zig
// std/fs.zig:14
pub const max_path_bytes = std.Io.Dir.max_path_bytes;
```

우리 코드가 이걸 반영한 모습:

```zig
// terminal/src/main.zig:40-45
const font_data = try std.Io.Dir.cwd().readFileAlloc(
    init.io,
    "vendor/fonts/Hanme_8x4x4.ttf",
    allocator,
    .unlimited,
);
```

예전이라면 `std.fs.cwd().readFileAlloc(allocator, path, max)`였다. 바뀐 점:
- `std.fs.cwd()` → `std.Io.Dir.cwd()`
- 첫 인자로 `io` 구현을 넘긴다
- 크기 제한이 `usize`가 아니라 `.unlimited` 같은 enum literal이다

왜 이렇게 바꿨나: I/O 구현을 교체 가능하게 만들기 위해서다. 같은 코드가
블로킹 스레드(`std.Io.Threaded`), io_uring(`std.Io.Uring`), 또는 아무것도
못 하는 `std.Io.failing`(freestanding)에서 돌 수 있다. ghostty가 이걸 실제로
활용한다.

```zig
// c/terminal.zig:52-80 (요약)
const Impl = if (builtin.os.tag != .freestanding) *std.Io.Threaded else void;

pub fn io(self: Io) std.Io {
    if (comptime builtin.os.tag == .freestanding) return std.Io.failing;
    return self.impl.io();
}
```

WASM(freestanding)에서는 I/O가 아예 없는 구현을 쓴다. `std.Io`가 인터페이스라서
가능한 구조다.

그래서 `ghostty_vt.Terminal.init`이 io를 요구한다.

```zig
// Terminal.zig:305-309
pub fn init(io_impl: std.Io, alloc: Allocator, opts: Options) !Terminal {
```

우리 `vt.zig:13`이 `io: std.Io`를 인자로 받아 그대로 전달하는 이유가 이것이다.

## 6.2 main의 새 시그니처

```zig
// terminal/src/main.zig:33
pub fn main(init: std.process.Init) !void {
// ghostty-src/example/zig-vt-stream/src/main.zig:4
pub fn main(init: std.process.Init) !void {
```

`std.process.Init`이 담고 있는 것 (std/process.zig:30-48 확인):

```zig
pub const Init = struct {
    minimal: Minimal,          // args, environ
    arena: *std.heap.ArenaAllocator,  // 프로세스 수명 전체
    gpa: Allocator,            // 임시 할당 (Debug에서 누수 검사)
    io: Io,                    // 타겟에 맞는 기본 I/O 구현
    environ_map: *Environ.Map,
    preopens: Preopens,

```

이전 버전의 `pub fn main() !void` + 직접 GPA 만들기 + `std.process.argsAlloc`
조합이 전부 여기로 통합됐다. 예제 코드에서 `init.gpa`, `init.io`가 갑자기
나오면 이 시그니처를 쓰고 있다는 뜻이다.

## 6.3 Writer / Reader 재작성, format 시그니처 변경

`std.io.Writer`(구)와 `std.Io.Writer`(신)는 다른 물건이다. 사용자 정의 포맷
함수의 시그니처가 바뀐 게 실무에서 제일 자주 걸린다.

```zig
// Parser.zig:93-103
pub fn format(
    self: CSI,
    writer: *std.Io.Writer,
) !void {
    try writer.print("ESC [ {s} {any} {c}", .{
        self.intermediates,
        self.params,
        self.final,
    });
}
```

예전에는 `format(self, comptime fmt: []const u8, options: FormatOptions, writer: anytype)`
로 인자가 넷이었다. 지금은 둘이다. 인터넷 예제에서 4인자 `format`을 보면
0.15 이전 코드다.

`std.debug.print`는 그대로 살아 있고(우리 코드가 계속 쓴다), 포맷 문자열
문법도 같다: `{s}` 문자열, `{d}` 십진수, `{any}` 아무거나, `{c}` 문자,
`{x}` 16진수.

## 6.4 ArrayList는 unmanaged가 기본

```zig
// std/std.zig:49, 58-59
pub fn ArrayList(comptime T: type) type { ... }
/// Deprecated; use `ArrayList`.
pub const ArrayListUnmanaged = ArrayList;
// std/array_list.zig:10-11
/// Deprecated.
pub fn Managed(comptime T: type) type { ... }
```

즉 이름이 뒤집혔다. 예전 `ArrayList`(allocator 내장)는 이제
`std.array_list.Managed`이고 deprecated다. 예전 `ArrayListUnmanaged`가 이제
그냥 `ArrayList`다.

옛날 예제 코드가 이렇게 생겼다면:

```zig
var list = std.ArrayList(u8).init(allocator);   // 0.16에서 안 됨
defer list.deinit();
try list.append(x);
```

0.16에서는:

```zig
var list: std.ArrayList(u8) = .empty;
defer list.deinit(allocator);
try list.append(allocator, x);
```

## 6.5 std.posix는 축소됐다

`std/posix.zig`는 0.16에서 1686줄이다(이전 버전 대비 크게 줄었다). 파일/디렉터리
관련 syscall 래퍼 상당수가 `std.Io` 밑으로 이동했다. 예전 코드의
`std.posix.open` / `std.posix.read` 류를 그대로 찾으면 없을 수 있다.

우리 프로젝트가 `std.posix` 대신 `@cImport`로 libc를 직접 부르는 것
(`drm.zig`, `pty.zig`)은 이 변화와도 무관하지 않다 — UAPI를 직접 다루는
코드라면 표준 라이브러리 재편에 덜 흔들린다.

## 6.6 build.zig의 모듈 중심 구조

```zig
// terminal/build.zig:12-35
const exe_mod = b.createModule(.{
    .root_source_file = b.path("src/main.zig"),
    .target = target,
    .optimize = optimize,
});
exe_mod.addIncludePath(b.path("vendor"));
exe_mod.addCSourceFile(.{ .file = b.path("src/stb_truetype_impl.c"), .flags = &.{} });
exe_mod.link_libc = true;
exe_mod.linkSystemLibrary("m", .{});

const ghostty_dep = b.dependency("ghostty", .{ .target = target, .optimize = optimize });
exe_mod.addImport("ghostty-vt", ghostty_dep.module("ghostty-vt"));

const exe = b.addExecutable(.{ .name = "terminal", .root_module = exe_mod });
b.installArtifact(exe);
```

핵심 변화: 예전에는 `addExecutable`에 `root_source_file`, `target`,
`optimize`를 직접 넘기고 exe에 대고 `addIncludePath`를 호출했다. 이제는
Module을 먼저 만들고 거기에 모든 설정(include path, C 소스, libc, import)을
붙인 다음, exe는 그 모듈을 `root_module`로 받는다.

`exe.linkLibC()` → `exe_mod.link_libc = true`, `exe.addIncludePath(...)` →
`exe_mod.addIncludePath(...)`로 옮겨간 것이다. 예제 코드가 exe에 대고
`addIncludePath`를 부르면 구버전이다.

의존성에 `.target`/`.optimize`를 반드시 넘겨야 한다는 것도 실전 교훈이다
(HANDOFF.md "plan과 달랐던 점" 1번). 안 넘기면 ghostty 모듈이 호스트 native로
빌드돼서 우리 `-mcpu=baseline` 설정과 충돌한다.

## 6.7 build.zig.zon

```zig

    .name = .tars_terminal,          // 문자열이 아니라 enum literal
    .version = "0.0.0",
    .fingerprint = 0x3a4ce1d146c5abb9,  // 0.14+에서 필수
```

`.name`이 `"tars_terminal"`(문자열)이 아니라 `.tars_terminal`(enum literal)인
것과 `.fingerprint`가 필수인 것이 최근 변화다. 원격 의존성은 `.url` + `.hash`
형태이고, ghostty의 zon이 그 예다.

```zig
// ghostty-src/build.zig.zon
.translate_c = .{
    .lazy = true,
    .url = "https://deps.files.ghostty.org/translate_c-....tar.gz",
    .hash = "translate_c-0.0.0-Q_BUWmU6BwB_9JKG2l2W7i_mhmYWeRseTGBEHi_YlV5f",
},
```

`.lazy = true`는 실제로 import될 때만 내려받는다는 뜻이다.

## 6.8 @cImport는 deprecated

0.16에서 `@cImport`는 deprecated 됐고, 권장 경로는 `c.h` 파일 하나를 만들어
`b.addTranslateC(...)`로 모듈화하는 것이다. 번역 결과 자체는 같다.

우리 코드(`drm.zig`, `pty.zig`, `font.zig`, `main.zig`)는 아직 `@cImport`를
쓰고 있고, ghostty는 `translate_c`를 외부 의존성으로 끌어다 쓰며 과도기를
넘기는 중이다. 지금 당장 깨지지는 않지만, 새로 쓰는 코드라면 `addTranslateC`
쪽을 고려한다.

## 6.9 로컬 패키지 캐시

0.16에서 패키지 캐시가 `~/.cache/zig` 전역에서 프로젝트 로컬
(`zig-pkg/`)로 바뀌었다. 그래서 `.gitignore`에 `terminal/zig-pkg/`가 들어가
있다.

# Day 7 — C interop과 OS 레벨 코드

우리 프로젝트가 실제로 하는 일이 여기다. TF-M3(evdev 키보드 입력)와 앞으로의
Rust → Zig 재작성이 전부 이 영역이다.

## 7.1 @cImport로 헤더 가져오기

```zig
// terminal/src/pty.zig:3-6
const c = @cImport({
    @cInclude("pty.h");
    @cInclude("unistd.h");
});
```

이러면 `c.forkpty`, `c.read`, `c._exit`, `c.pid_t`가 생긴다. 내부적으로
translate-c가 헤더를 Zig 소스로 번역한다.

빌드 쪽 설정이 짝을 이룬다.

```zig
// terminal/build.zig:17-23
exe_mod.addIncludePath(b.path("vendor"));
exe_mod.addCSourceFile(.{ .file = b.path("src/stb_truetype_impl.c"), .flags = &.{} });
exe_mod.link_libc = true;
exe_mod.linkSystemLibrary("m", .{});
```

- `addIncludePath` — `@cInclude`가 찾을 경로
- `link_libc = true` — libc 링크 (`@cImport`로 libc 헤더를 쓰면 거의 필수)
- `addCSourceFile` — C 소스를 같이 컴파일 (stb는 헤더 온리 라이브러리라
  구현부를 켜는 `.c` 파일이 하나 필요하다)

## 7.2 translate-c의 타입 매핑

| C | Zig (translate-c 결과) |
|---|---|
| `int` | `c_int` |
| `unsigned long` | `c_ulong` |
| `char*` | `[*c]u8` |
| `const char*` | `[*c]const u8` |
| `void*` | `?*anyopaque` |
| `struct Foo` | `extern struct` |
| `#define FOO 1` | `pub const FOO = 1;` (가능한 경우) |
| 함수형 매크로 | 대개 번역 실패 → 손으로 다시 씀 |
| 비트필드 있는 struct | opaque 타입으로 강등 (알려진 한계) |

`[*c]T`는 "C 포인터"다. null도 될 수 있고, 단일/다중 항목 구분도 없다. 편의를
위해 Zig 포인터와 자동 변환되지만, 그만큼 안전성이 없다. 가능하면 경계에서
`[*]T`나 `[]T`로 좁히는 게 좋다.

## 7.3 @cImport가 만든 시그니처가 안 맞을 때

우리가 실제로 겪은 사례다.

```zig
// terminal/src/pty.zig:8-12
/// libc의 execv를 직접 선언한다. @cImport가 만들어주는 `c.execv`는
/// `char *const argv[]`를 `[*c]const [*c]u8`(비-const u8 포인터의 배열)로
/// 옮기기 때문에 Zig의 `?[*:0]const u8` 배열을 그대로 넘길 수 없다.
/// const를 벗기는 캐스팅을 하느니 처음부터 맞는 시그니처로 선언한다.
extern "c" fn execv(path: [*:0]const u8, argv: [*:null]const ?[*:0]const u8) c_int;
```

`extern "c" fn 이름(...) 반환타입;`은 "이 심볼은 libc에 있다, 내가 말한 대로
호출하겠다"는 선언이다. 링커가 심볼을 찾아준다.

이 기법이 강력한 이유: C 헤더의 부정확한 타입(특히 const 자격)에 끌려다니지
않고 Zig 쪽에서 정확한 타입을 정할 수 있다. 대신 시그니처를 틀리면 컴파일러가
못 잡는다 — ABI 수준에서 맞는지는 사람이 보증한다.

## 7.4 UAPI 구조체를 손으로 옮기기

`drm.zig`는 `@cImport`로 DRM 헤더를 가져오지 않는다. 구조체를 전부 손으로
`extern struct`로 옮겼고, 매크로까지 재구현했다.

```zig
// terminal/src/drm.zig:107-110
fn drmIowr(comptime T: type, nr: u32) u32 {
    const drm_ioctl_base: u32 = 'd';
    return (@as(u32, 3) << 30) | (drm_ioctl_base << 8) | nr | (@as(u32, @sizeOf(T)) << 16);
}
```

이건 리눅스의 `_IOWR(type, nr, size)` 매크로다. 비트 배치는:

```
 31 30 29                16 15            8 7             0
+-----+--------------------+---------------+---------------+
| dir |        size        |     type      |      nr       |
+-----+--------------------+---------------+---------------+
  3 = READ|WRITE            'd' = DRM
```

`@sizeOf(T)`가 컴파일 타임에 구조체 크기를 넣어주므로, C 매크로가 하던 일을
그대로 한다. `comptime T: type` 파라미터 덕분에 타입마다 따로 쓸 필요가 없다.

왜 `@cImport`를 안 썼나: translate-c는 함수형 매크로를 번역하지 못하고,
비트필드가 있는 구조체를 opaque로 강등시킨다(ziglang/zig#1499, #4001). 커널
UAPI 헤더에서 실제로 문제가 되는 지점이다. TF-M3에서 `linux/input.h`의
`struct input_event`를 시도할 때 같은 벽을 만날 수 있다.

여기서 얻는 교훈이 하나 있다. "Zig는 C를 그냥 가져다 쓴다"는 말은 응용 계층
라이브러리에서는 대체로 참이지만, 커널 UAPI 영역에서는 성립하지 않는다.
Zig의 실질적 강점은 오히려 툴체인 쪽이다 — 배포판 하나에 Clang과 여러 libc
헤더가 들어 있어 `x86_64-linux-gnu.2.28`처럼 glibc 버전까지 지정한 크로스
컴파일이 된다.

## 7.5 포인터 캐스팅과 volatile

```zig
// terminal/src/drm.zig:122
pixels: [*]volatile u8,

// terminal/src/drm.zig:128-132
pub fn setPixel(self: Framebuffer, x: u32, y: u32, color: u32) void {
    const offset = y * self.pitch + x * 4;
    const ptr: *volatile u32 = @ptrCast(@alignCast(self.pixels + offset));
    ptr.* = color;
}
```

읽는 법:
- `volatile` — 이 메모리는 컴파일러가 모르는 이유로 변한다(또는 쓰기가
  관측된다). 최적화로 읽기/쓰기를 지우면 안 된다. mmap된 프레임버퍼가 딱
  그런 메모리다.
- `self.pixels + offset` — 다중 항목 포인터에는 산술 연산이 된다 (`[*]T`이므로).
  `[]T` 슬라이스였다면 `self.pixels[offset..]`을 썼을 것이다.
- `@alignCast` — u8 포인터(정렬 1)를 u32 포인터(정렬 4)로 만들려면 정렬을
  올려야 한다. Safe 모드에서 실제로 정렬이 안 맞으면 패닉한다.
- `@ptrCast` — 타입 재해석.
- `ptr.*` — 포인터 역참조. Zig는 `->`가 없고 항상 `.*`다.

`@ptrCast(@alignCast(...))` 조합은 바이트 버퍼를 타입 있는 뷰로 볼 때
반복해서 나오는 관용구다.

포인터 ↔ 정수 변환도 UAPI에서 필수다.

```zig
// terminal/src/drm.zig:171-173
res.crtc_id_ptr = @intFromPtr(crtc_ids.ptr);
res.connector_id_ptr = @intFromPtr(connector_ids.ptr);
res.encoder_id_ptr = @intFromPtr(encoder_ids.ptr);
```

커널 구조체의 필드가 `__u64`인데 실제로는 포인터를 담는다. `@intFromPtr`로
주소를 정수로 만들어 넣는다. 32/64비트 호환을 위한 커널 UAPI의 흔한 관례다.

`drm.zig:159-183`의 "두 번 ioctl" 패턴도 UAPI 관용구다. 한 번은 개수를 알아내려고,
두 번째는 실제로 배열을 채우려고 호출한다.

## 7.6 anyopaque

```zig
// terminal/src/drm.zig:112
fn drmIoctl(fd: c_int, request: u32, arg: *anyopaque) !void {
```

`anyopaque`는 C의 `void`(불완전 타입)에 해당한다. `*anyopaque`가 `void*`다.

Q. `@cImport`가 만든 `c.execv`를 안 쓰고 `extern "c" fn execv`를 직접 선언한
것이 안전한가?
A. 링커가 심볼 이름은 확인해주지만 시그니처는 확인하지 않는다. 그래서 ABI
수준에서 인자 개수/크기/호출 규약이 맞는지는 사람이 보증해야 한다. 이 경우
`char *const argv[]`와 `[*:null]const ?[*:0]const u8`은 둘 다 "null로 끝나는
포인터 배열의 첫 원소 주소"라 ABI가 동일하다. const 차이는 컴파일 타임 개념일
뿐 런타임 표현에 영향이 없다.

Q. `pixels: [*]volatile u8`에서 `volatile`을 빼면 무엇이 깨지는가?

제거할 수 있다. mmap된 GPU 메모리는 부수효과가 목적이므로 그 최적화가 틀렸다.
`volatile`이 그 최적화를 금지한다.

# 부록 C — 흔한 함정

- 슬라이스를 반환하면서 그 backing 메모리를 defer로 해제하기. 소유권을
  넘길 땐 `toOwnedSlice` 또는 `errdefer`.
- `@intCast`로 음수를 부호 없는 타입에 넣기. Safe 모드에서 패닉한다.
- `extern struct`를 써야 할 자리에 `struct`. 필드 순서가 보장되지 않아
  커널/C에 쓰레기가 간다.
- `packed struct`의 미초기화 union 변형. 0으로 `@bitCast` 후 채운다.
- `@cImport` 결과의 const 자격을 캐스팅으로 우회. 대신 `extern "c" fn`으로
  올바른 시그니처를 직접 선언한다.
- 컨테이너에서 `alloc`을 빼먹기. 0.16 unmanaged 메서드는 전부 alloc을 받는다.
- 인터넷 예제를 그대로 붙여넣기. Day 6 체크리스트를 먼저 돌린다.
